# 06 · 权限 / 超时释放 / 幂等与审计

这一篇是「把系统变成能交给别人用的系统」的四块工程化补齐：
**谁能干什么（权限）**、**锁死的库存怎么办（超时释放）**、
**重复提交怎么办（幂等）**、**出了事怎么查（审计）**。

它们不是新业务功能，而是让前面五个模块**敢放到生产环境**的前提。

---

## 1. 权限

### 1.1 认证和授权是两件事

| | 问题 | 本项目怎么做的 |
|---|---|---|
| **认证** Authentication | 你是谁？ | `JwtInterceptor` 解析 token → 放进 `UserContext` 和 `SecurityContext` |
| **授权** Authorization | 你能干什么？ | `@PreAuthorize` 按角色拦接口 |

只做认证不做授权，等于「谁都能进，进去了什么都能干」。

### 1.2 三个角色

| 角色 | 能干什么 | 不能干什么 |
|---|---|---|
| `ADMIN` 系统管理员 | 一切 + 用户管理 | —— |
| `MANAGER` 仓库主管 | 主数据维护、库存调整（冻结/移库/盘点/对账）、单据作业 | 用户管理 |
| `OPERATOR` 作业员 | 收货、上架、拣货 + 全部查询 | 主数据、库存调整、用户管理 |

依据是 docs/01 第 2 节：「主管负责单据审核、库存调整、盘点」。

**为什么只用三个角色、不做权限点表**：RBAC 做到「角色→权限点→接口」更灵活，
但要配套权限管理界面、缓存、动态菜单，和学习项目的收益不成正比。
升级路径是清晰的：把 `@PreAuthorize` 里的角色换成权限点即可。

### 1.3 为什么 `@PreAuthorize` 能生效（一个关键细节）

项目原来把 Spring Security 的 filter chain 全部 `permitAll`，
真正的鉴权放在 MVC 拦截器里。这种情况下 `@PreAuthorize` 是**用不了的** ——
它读的是 `SecurityContext`，而那个上下文当时是空的（判成匿名 → 全部 403）。

修法是让 `JwtInterceptor` 在解析完 token 之后**同步一份身份到 SecurityContext**：

```java
List<GrantedAuthority> authorities = StringUtils.hasText(role)
        ? List.of(new SimpleGrantedAuthority("ROLE_" + role))
        : List.of();
SecurityContextHolder.getContext()
        .setAuthentication(new UsernamePasswordAuthenticationToken(username, null, authorities));
```

两个必须注意的点：

1. **权限名要带 `ROLE_` 前缀**：`@PreAuthorize("hasRole('ADMIN')")` 里 Spring 会自动补前缀。
2. **`afterCompletion` 必须 `SecurityContextHolder.clearContext()`**：
   和 `UserContext.clear()` 同理 —— Tomcat 复用线程，不清就会把上一个用户的角色留给下一个请求。

### 1.4 前端过滤的定位：体验，不是安全边界

前端做了三件事：菜单按角色过滤、路由 `meta.roles` 拦截、无权限时提示并送回工作台。

但**藏起来的菜单挡不住直接敲 URL 或直接发请求的人**。
所以两层的分工是：

- **后端 `@PreAuthorize`**：保证「干不了」（403 + code 20003）
- **前端过滤**：保证「看不到、不用点」，避免作业员看到一个点啥都报错的空壳页面

### 1.5 用户管理的两条自我保护

删自己、禁用自己、把最后一个启用的管理员降级 —— 这三件事的共同点是：
**做完之后可能没人能再进后台了**。所以后端直接拒绝（20006 / 20007）：

```java
if (id.equals(UserContext.getUserId()) && newStatus == STATUS_DISABLED) {
    throw new BizException(AuthErrorCode.SELF_PROTECTED);
}
if (wasAdmin && !stillAdmin) {
    ensureAnotherEnabledAdmin(id);   // 没有别的启用管理员 → 20007
}
```

密码永远只存 BCrypt 哈希：没有「查密码」接口，忘记了只能由管理员重置。

## 2. 超时释放（BR-010）

### 2.1 要解决什么

出库单分配之后，库存被 `locked_qty` 占住 —— 货还在货架上，但**别人用不了**。
如果这单一直没人处理，那批货就被永久锁死：没有任何报错，看板上还显示「有货」。
这类「静默锁死」是最难被发现的问题。

### 2.2 怎么做

```
每 60 秒扫一遍：status = 'ALLOCATED' 且 allocate_time < now - 30 分钟
        ↓
① 作废该单下所有未完成的拣货任务（task 模块自己的表）
② 调 outbound 模块的 release()：把 locked_qty 还回去，单据回 CREATED
```

**只处理 `ALLOCATED`，绝不碰 `PICKING`**：
到了 PICKING 说明货可能已经被从货架上拿下来了，把锁定还回去会造成账实不符
（见 `OutboundStatus.canRelease` 的注释）。这是设计上划死的边界，不是漏掉的。

**为什么放在 task 模块**：这个动作要同时碰 task 和 outbound 两张表，
而 docs/02 定的依赖方向是 `task → outbound`，所以编排在 task 这边；
出库模块只暴露 `listTimeoutAllocatedOrderIds`（读）和 `release`（写自己的表）。

### 2.3 三个工程细节

1. **每条单据单独 try-catch**：一张单释放失败（比如期间被推进到 PICKING）
   不能让整批扫描中断。定时任务的正确姿势是「能做多少做多少」。
2. **定时任务线程要被标成「系统」**：
   ```java
   UserContext.set(SYSTEM);   // 流水里记「系统（超时释放）」
   try { ... } finally { UserContext.clear(); }   // 必须清，线程是复用的
   ```
   不设的话，库存流水里的操作人会是空的 —— 事后没人知道是谁放的。
3. **空跑不打日志**：绝大多数轮次没有超时单，打日志只会把真正的问题淹掉。

### 2.4 为什么现在不用 MQ 延迟队列

第 8 周才引入 MQ。现在这条路（定时扫描 + 状态机 CAS）跑通之后，
升级到延迟队列只是把「扫描」换成「消息到期投递」，**释放逻辑一行都不用改**。

定时任务的三个已知代价（面试会被问）：

| 代价 | 说明 | 升级方向 |
|---|---|---|
| 有延迟 | 扫描间隔多长，最坏就晚多久释放 | 延迟队列按 deadline 精确投递 |
| 有空转 | 没有超时单时也在扫 | 只返回命中的行 + 走 `idx_allocate_time` 索引 |
| 多实例重复扫 | 单机没问题，多实例会重复处理 | 分布式锁，或改成 MQ 投递 |

（第 3 条实际是安全的：即使两个实例同时扫到同一张单，
`release()` 内部的状态 CAS 也只会让一个成功 —— 这就是「状态机兜底」。）

## 3. 幂等

### 3.1 先分清：哪些接口需要幂等键

| 类型 | 例子 | 要不要 |
|---|---|---|
| **跃迁**（状态从 A 到 B，做过就回不去） | 领取/开始/完成任务、分配、发货 | ❌ 状态机的 CAS 已经保证只发生一次 |
| **累加 / 新建**（重复做就是真的做两次） | 创建单据、**收货**、冻结/移库/盘点 | ✅ 需要 |

判断标准一句话：**这个操作的效果是「累加」还是「跃迁」？**

这里有个容易混的点：

| | `inventory.version` 的 CAS | `stock_task.status` 的 CAS |
|---|---|---|
| 防什么 | **并发覆盖**（后写的覆盖先写的） | **重复意图**（同一件事做两次） |
| 同一意图提交两次 | 两次**都会成功**（版本每次都是新的） | 第二次**必然失败**（状态回不去了） |

所以「库存变动要额外幂等」和「任务不用幂等」并不矛盾。

**收货为什么最危险**：一张单允许分批收货，单据状态一直停在 `RECEIVING`，
数量上限也挡不住（预计 100，收 30 再收 30 是合法的）。
唯一能识别「这就是刚才那次提交」的，只有业务键 + 请求体哈希。

### 3.2 表怎么用

`idempotent_record`（V1.0.0 建表，V1.0.2 补了 `error_msg`）：

```
idempotent_key  唯一索引 —— 它才是那把锁
status          0 处理中 / 1 成功 / 2 失败
result_snapshot 成功响应的 JSON，重复请求直接拿它重放
error_msg       失败原因
expire_time     过期时间，定时任务分批清理
```

一次请求的流程：

```
① 拼 key：bizType + (请求头 key | SpEL 业务键 | anon) + 请求体哈希
② 抢位（靠唯一索引，不是先查再插）
     ├─ 抢到 → 执行业务 → 成功写快照 / 失败记原因
     ├─ 命中成功 → 直接重放快照，业务一行都不执行
     ├─ 命中处理中 → 看租约：
     │     ├─ 租约没过期 → 人家确实在跑 → 10007「请勿重复提交」
     │     └─ 租约已过期 → 判定持锁进程已死 → CAS 接手执行
     └─ 命中失败 → 放行重试
```

**为什么 key 里一定要带请求体哈希**：同一个业务键下，
「内容不同的两次请求」是两件事 —— 比如分批收货，收 30 件再收 30 件必须都能执行；
只有内容完全相同的重复提交才是要挡的。

**为什么抢位记录要立刻提交**：并进业务事务的话，业务还没提交时别的线程看不到它，
去重就推迟到了「业务提交之后」—— 而重复请求恰恰是同一瞬间发生的。
实现上靠「单条语句自动提交」，顺带获得一个好处：唯一键冲突只影响那一条语句，
不会把事务标记成 rollback-only。

### 3.3 踩到的两个坑（都留了回归测试）

**坑 1：`INSERT ... ON DUPLICATE KEY UPDATE id = id` 判断不出「插入还是命中」**

直觉上它返回 0 表示已存在。但 MySQL 的 affected rows 受连接参数
`CLIENT_FOUND_ROWS` 影响（Connector/J 默认开着）：
条件匹配但值没变的 UPDATE 返回的是「匹配行数 1」，不是「修改行数 0」。

症状：同一个 key 提交两次，**建了两张入库单**，幂等记录却只有一条。

修法：换成 `INSERT ... SELECT ... WHERE NOT EXISTS`，语义就确定了
（真的插进去 = 1；被 WHERE 挡掉 = 0），并发下由唯一索引兜底并捕获重复键。

**坑 2：重放时用 `Object.class` 反序列化 → ClassCastException**

切面包着的是 `Result<Long> create(...)`，Spring 代理会把通知的返回值按声明类型强转。
用 `Object.class` 反序列化得到的是 `LinkedHashMap`，一返回就炸。
必须按方法真实返回类型反序列化：

```java
objectMapper.readValue(snapshot, ((MethodSignature) pjp.getSignature()).getReturnType());
```

**坑 3：抢位记录没人收尾，会把用户永久挡死**

抢位记录是**独立提交**的（必须这样，否则别的线程看不到它）。
好处是去重立刻生效，代价是它**不受业务事务保护**：

- 「业务抛异常」能被 catch 到 → `markFailed` 把它改成 status=2，下次还能重试 ✔
- 「进程直接死掉」（重启 / OOM / kill -9）**没有任何代码有机会执行** →
  那行记录永远停在 status=0，之后同 key 的请求全被 10007 挡住，
  而用户其实什么都没做成

**这不是理论问题**：开发期每改一次代码就重启一次后端，
重启时正好有写请求在飞，就会留下这样一条记录。

修法是给「处理中」加**租约**（V1.0.3 加的 `locked_until`）：
「处理中」不再是无限期的，而是「我预约占用 30 秒」。

```java
boolean leaseExpired = existing.getLockedUntil() == null
        || existing.getLockedUntil().isBefore(LocalDateTime.now());
if (!leaseExpired) {
    return AcquireResult.processing();          // 人家确实在跑，拒绝
}
// 租约过期 → 判定持锁进程已死，CAS 接手（并发的两个重试只有一个能改成功）
int preempted = recordMapper.preempt(safeKey, requestHash, lockedUntil);
```

再加一道定时兜底：租约过期超过 **60 分钟**还停在处理中的，直接标成 status=2（失败）——
免得根本没人重试的记录永远显示「处理中」。

**这个方案自己也有代价，必须一起想清楚**：

> 租约过期就放行，意味着如果第一个请求**其实没死、只是特别慢**，
> 第二个请求会和他同时执行 → 真的重复。

所以三条纪律：

1. **租约必须远大于业务耗时**：本项目接口是毫秒级，30 秒是三个数量级的余量。
   代码注释里写死了「千万别改小」。
2. **兜底阈值要远大于租约**（60 分钟 vs 30 秒）：刚过期的记录要留足「用户自己重试」的机会，
   不能立刻被判死刑。
3. **最后一道防线永远是业务本身**：重复收货会被「实收不能超过预计」挡住、
   重复发货会被状态机挡住。幂等表是**第一道**防线，不是唯一一道 ——
   这也是为什么前面要按「跃迁」和「累加」两类接口分开处理。

### 3.4 哪些接口加了

| 接口 | bizType | 业务键 | TTL |
|---|---|---|---|
| 创建入库单 / 出库单 | `INBOUND_CREATE` / `OUTBOUND_CREATE` | 请求头 UUID | 24h |
| 收货 | `INBOUND_RECEIVE` | `#id`（单据 id） | 10 分钟 |
| 冻结 / 解冻 | `INVENTORY_FREEZE` / `INVENTORY_UNFREEZE` | `#id`（库存行 id） | 10 分钟 |
| 移库 / 盘点 / 对账 | `INVENTORY_TRANSFER` 等 | anon（只靠请求体哈希） | 10 分钟 |

收货/库存作业的 TTL 取 10 分钟：现场高频动作，去重窗口短一点，减少误挡
（「内容相同但确实要执行两次」的概率，比「手抖点两次」低得多）。

前端配合：`useIdempotentKey()` 在**一次动作开始时**生成一个 UUID，
双击 / 重试 / 超时重发都用同一个，**成功之后才换新的**。
每次请求都重新生成的话，幂等就形同虚设。

## 4. 审计日志

### 4.1 切面自动记录，不靠注解

```java
@Around("execution(public * com.myproject.wmsserver..controller..*(..)) && ("
        + "@annotation(PostMapping) || @annotation(PutMapping) || @annotation(DeleteMapping))")
```

**为什么不用 `@AuditLog` 注解式**：注解的问题不是麻烦，而是**会漏**。
新加一个写接口忘了标，那条链路就静默地没有审计 —— 而且没人会发现，
直到出了事要查「是谁改的」才反应过来。按「控制器 + 写映射」自动切，新增接口天然被覆盖。

### 4.2 记什么

| 字段 | 取值 |
|---|---|
| traceId | 和请求日志同一个，两边能对上 |
| user / module / action | `admin` / `inbound` / `POST receive` |
| target | `InboundOrder:521`（参数里第一个数字当对象 id） |
| detail | 请求参数 JSON，**密码字段脱敏成 `***`** |
| result / errorMsg / costMs | 成功失败、失败原因、耗时 |

三个刻意的选择：

1. **只记写接口**：查询量大又没有变更语义，全记只会把表撑爆。
2. **失败也要记**：「谁试图改但没改成」往往更值得看（越权尝试、重复提交、规则拦截）。
3. **日志写失败绝不影响业务**：整段包在 try-catch 里，最坏只是少一条审计记录。

一个副作用值得一提：被幂等拦下来的重复请求**也会进审计**（切面顺序是审计在外层），
所以「谁在什么时候重复提交了什么」在审计表里查得到；那条记录的 `costMs` 会是 0。

### 4.3 同步写与升级方向

现在是同步写一条（几毫秒）。异步要么可能丢日志，要么得引入 MQ（第 8 周）。
升级路径：把 `auditLogMapper.insert` 换成发一条 MQ 消息，由消费端落库。

## 6. 遗留

1. ~~任务级超时（TaskStatus.TIMEOUT → 回任务池重试一次）~~ —— **已解决**：
   任务创建时就带 deadline（上架 120 分钟 / 拣货 30 分钟，可配），过期先标 TIMEOUT，
   再【只】重新入池一次（顺延时限、清掉领取人）；重试过就停在 TIMEOUT 等人处理。
   详见 StockTaskTimeoutJob / StockTaskTimeoutTest。
2. **修改密码后旧 token 仍然有效**（无状态 JWT 的固有代价）。
   想立刻失效需要 token 黑名单（Redis）或把有效期改短。
3. ~~审计日志只写不查~~ —— **已解决**：新增 /system/audit-logs 查询接口 + 前端「操作日志」页，
   支持按操作人/模块/结果/traceId/时间区间检索，点行看请求参数详情（密码已脱敏）。
   仍可优化：数据量大了应该把列表和详情拆成两个接口。

所以「谁在什么时候重复提交了什么」在审计表里查得到；那条记录的 `costMs` 会是 0。

### 4.3 同步写与升级方向

现在是同步写一条（几毫秒）。异步要么可能丢日志，要么得引入 MQ（第 8 周）。
升级路径：把 `auditLogMapper.insert` 换成发一条 MQ 消息，由消费端落库。
