# 07 · 数据库表结构笔记

> 覆盖 `db/migration/V1.0.0 ~ V1.0.7`，共 **21 张表**。
> 目标：看完能回答「每张表是干嘛的、为什么这么设计、面试怎么讲」。

---

## 0. 阅读地图：按「依赖层级」看，不要按脚本顺序看

```
第一层  主数据（描述"有什么"）
        sys_user   warehouse   zone   location   product   partner
                       │          │       │
第二层  库存核心（描述"现在有多少"）
        inventory  ────┴──────────┴───────┘      inventory_transaction
                             ▲
第三层  单据（描述"要做什么"）
        inbound_order(+item)      outbound_order(+item)+outbound_allocate
        stocktaking_order(+item)  transfer_order(+item)
                             │
第四层  执行（描述"谁去干"）
        stock_task
                             │
第五层  支撑（让上面几层不出错）
        sys_sequence   idempotent_record   audit_log
```

**一句话记住全库**：主数据定骨架 → 库存是唯一事实 → 单据驱动库存变化 → 任务派给人干活 → 流水/幂等/审计负责"事后可追溯、重复不出错"。

**铁律**：库存数量只能通过 `InventoryService.applyChange` 改，任何单据都不许直接 `UPDATE inventory.qty`。每次改动必须同时落一条 `inventory_transaction`。

## 1. 通用设计套路（先看这个，后面 21 张表就不用重复解释了）

这 21 张表有大量"长得一样"的字段，理解了它们，读表速度翻倍。

### 1.1 审计四件套（几乎所有业务表都有）

```sql
create_time datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
update_time datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
create_by   bigint NULL
update_by   bigint NULL
```

- `datetime(3)` = 毫秒精度。并发下秒级时间戳会撞车，排序/去重都靠它。
- `ON UPDATE` 由数据库自动维护，**不要**在代码里手动 set update_time。

### 1.2 逻辑删除

```sql
deleted tinyint NOT NULL DEFAULT 0
```

所有查询都要带 `AND deleted = 0`。**注意坑**：唯一索引大多**没有**把 `deleted` 包进去（见 `warehouse.uk_code`），所以删掉的记录编码**不能复用**。脚本注释里写明了原因：加进 `deleted` 会导致"同一编码删两次"冲突，真要支持复用得改成时间戳型删除标记。

### 1.3 冗余快照字段（不是设计冗余，是刻意的）

单据明细里出现 `sku_code` / `sku_name` / `location_code` 这类"明明能 join 出来"的字段，是因为：

> 商品改了名字，一年前的单据显示的必须还是当时的名字。只存 id 会让历史单据跟着主数据一起变 —— 财务最忌讳这个。

V1.0.4/V1.0.5 里 `partner` 也是同样思路：**同时存 id（用来统计关联）+ 名称快照（用来固化历史）**。

### 1.4 空串 vs NULL 的选择（面试高频）

| 场景 | 选择 | 原因 |
|---|---|---|
| `inventory.batch_no` 无批次 | `NOT NULL DEFAULT ''` | NULL 会**破坏唯一约束**（MySQL 唯一索引允许多个 NULL），两条无批次库存就撞不掉了 |
| `product.barcode` 可为空 | `NULL` | 反过来：这里就是希望"多条空条形码互不冲突" |

同一个库里两种选择相反，但都有明确理由 —— 这是很好的讲解素材。

### 1.5 CHECK 约束兜底

MySQL 8.0.16+ 才真正生效。用来在**数据库层**挡住脏数据，比如 `chk_inventory_qty` 保证 `locked + frozen <= qty`。即使应用层有 bug，数量也不会变成负数。

## 2. 第一层：主数据

### 2.1 `sys_user` —— 系统用户

| 字段 | 说明 |
|---|---|
| `username` | 唯一键，登录名 |
| `password` | BCrypt 哈希（`$2a$10$...`），**绝不存明文** |
| `role` | `ADMIN` / `MANAGER` / `OPERATOR` |
| `status` | 1 启用 / 0 禁用 |

- 种子账号：`admin / 123456`。
- 只有 3 个角色、没有角色表、没有权限表 —— 权限靠注解 + 角色判断，是刻意做轻的。

### 2.2 `warehouse` —— 仓库

- `code` 全局唯一（`uk_code`），`status`：`ENABLED` / `DISABLED`。
- 顶级容器，几乎所有业务表都带 `warehouse_id`（冗余但值得，避免层层 join）。

### 2.3 `zone` —— 库区

- 挂在仓库下，`uk_wh_code (warehouse_id, code)` —— **仓库内唯一**，不是全局唯一。
- `zone_type`：`STORAGE` 存储区 / `PICKING` 拣货区 / `RECEIVING` 收货区 / `SHIPPING` 发货区。
- `sort_no` 排序号。

### 2.4 `location` —— 库位

- 三级结构的**末级**，也是库存真正挂载的地方：`warehouse → zone → location`。
- `location_type`：`RACK` 货架 / `FLOOR` 地面 / `TEMP` 暂存。
- `capacity` / `used_capacity`：容量上限与已用，**和上架在同一个事务里维护**。
  - `capacity = 0` 表示不限（如收货暂存位）。
  - 坑：`used_capacity` 是冗余字段，任何绕过服务层直接改 `inventory` 的代码都会让它失真。
- `status` 比别的表多一个 `FROZEN`（冻结，不允许作业）。

### 2.5 `product` —— 商品 SKU

- `sku_code` 全局唯一，`barcode` 唯一但可 NULL。
- 有体积（`length/width/height_mm`）、`weight_g` —— 为将来的**库位容量/装载率计算**留的。
- `shelf_life_days` 保质期天数，`0` 表示不管效期。配合 `inventory` 的 `production_date`/`expiry_date` 做 **FIFO 与效期预警**。

### 2.6 `partner` —— 往来单位（V1.0.4 新增）

- `partner_type`：`SUPPLIER` 供应商 / `CUSTOMER` 客户，**合成一张表**。
- 设计取舍（注释原话）：两者字段几乎一样，拆两张表唯一好处是约束更严，代价是 CRUD 写两遍；真出现"供应商有账期、客户有信用额度"的分化时再拆不迟。
- `code` 是**跨类型全局唯一**，将来统一对账不会撞号。
- 单据侧通过 V1.0.5 加的 `inbound_order.supplier_id` / `outbound_order.customer_id` 引用，**允许 NULL**（历史数据没有 id，不能编造）。

## 3. 第二层：库存核心（最重要，面试主战场）

### 3.1 `inventory` —— 库存余额

唯一键 `uk_loc_sku_batch (location_id, sku_id, batch_no)`：**一个库位 + 一个 SKU + 一个批次 = 一行库存**。这是整个系统的粒度基准。

**四种数量（必须背下来）：**

| 字段 | 含义 |
|---|---|
| `qty` | 在库实物数量（账面上真实有多少货） |
| `locked_qty` | 锁定数量（已分配给出库单、还没拣走） |
| `frozen_qty` | 冻结数量（盘点中 / 质检中，动不了） |
| `available_qty` | **生成列** = `qty - locked_qty - frozen_qty`，真正能动的量 |

```sql
available_qty int GENERATED ALWAYS AS (qty - locked_qty - frozen_qty) STORED
```

- 生成列由数据库算，**改不了也用不着改**，杜绝了"三个数量对不上"的经典 bug。
- 建了 `idx_available (sku_id, warehouse_id, available_qty)` —— 分配库存时直接按可用量筛选。

其余关键点：
- `version`：**乐观锁版本号**。更新时 `WHERE version = ?`，更新不到说明被并发改过，重试或报错。这是不用 `SELECT FOR UPDATE` 的高并发方案。
- `inbound_time`：**只写一次**的首次入库时间，FIFO 排序依据（`idx_fifo (sku_id, warehouse_id, inbound_time)`）。
- `production_date` / `expiry_date`：效期与先进先出。
- CHECK：`locked_qty + frozen_qty <= qty`，三个数量都 >= 0。

### 3.2 `inventory_transaction` —— 库存流水

**只增、不改、不删**（表注释写死的）。这是库存的"账本"：

- `tx_no` 唯一，同时是**幂等键** —— 重复提交同一个流水号只能成功一次。
- `qty_change` / `locked_change` / `frozen_change`：三类变动，可正可负。
- `qty_before` / `qty_after`：变动前后快照，反向推导/对账用。
- `source_type` / `source_id` / `source_no`：追溯来源（`INBOUND_ORDER` / `OUTBOUND_ORDER` / `TASK` / `MANUAL` / `STOCKTAKING`）。
- `operator_name` 是快照，不是外键。

**为什么必须有这张表**：`inventory` 只存"现在多少"，一旦数据对不上，没有流水就永远查不出是哪一步错的。它也是盘点差异分析、库存轨迹查询的数据源。

## 4. 第三层：单据

### 4.1 `inbound_order` + `inbound_order_item` —— 入库单

主表：`order_no`（`IN + yyyyMMdd + 6位序号`）、`supplier_id`(V1.0.5) + `supplier_name`(快照)、`expect_arrive_time`。

**状态机**：
```
CREATED → RECEIVING → RECEIVED → PUTAWAY_DONE → CLOSED
    └──────────────────────────────────────────→ CANCELLED
```

明细表三个数量，务必分清：

| 字段 | 含义 |
|---|---|
| `expect_qty` | 预计收多少 |
| `received_qty` | 实际收了多少（收货环节写） |
| `putaway_qty` | 已上架多少（上架环节写） |

**收货 ≠ 上架**。收货后货在暂存区，上架任务完成后库存才真正进库位。这个分离是 WMS 的标准模型。

### 4.2 `outbound_order` + `outbound_order_item` —— 出库单

主表：`order_no`（`OUT...`）、`customer_id`(V1.0.5) + `customer_name`(快照)、`expect_ship_time`。

**状态机**：
```
CREATED → ALLOCATED → PICKING → PICKED → SHIPPED → CLOSED
    └─────────────────────────────────────────────→ CANCELLED
```

三个数量：`total_qty`（需求）、`allocated_qty`（已分配）、`picked_qty`（已拣货）。

- `allocate_time`：分配完成时间，配合 `idx_allocate_time (status, allocate_time)` 做**超时释放** —— 定时任务扫"分配了但久久没拣"的单，把锁定的库存放回去。
- V1.0.6 新增 `reverse_of_id` / `reversed_by_id`：**红冲**。已发货的单不可撤销，只能再开一张反向单冲掉。
  - `uk_reverse_of` 唯一索引保证一张原单只能被红冲一次（MySQL 唯一索引允许多个 NULL，非红冲单不受影响）。

### 4.3 `outbound_allocate` —— 出库库存分配明细

**这张表是"锁定"的载体**，理解它才能讲清出库。

- 一行 = 「某张出库单的某条明细」占用了「某条 inventory」的多少数量。
- 分配时：`inventory.locked_qty += N`；拣货完成：`locked_qty -= N, qty -= N`。
- `status`：`LOCKED`（锁着）→ `PICKED`（已拣）或 `RELEASED`（释放了，超时/取消）。
- 存了 `inventory_id` + `location_id` + `batch_no` 冗余 —— 一是避免 join，二是**锁定那一刻的库位/批次要固化**，不能被后续移库改掉。

### 4.4 `stocktaking_order` + `stocktaking_order_item` —— 盘点单（V1.0.7）

- 单头锁**一个库位**（`location_id`），明细是该库位下的每个库存行。
- 明细三个"建单时快照"：`system_qty` / `locked_qty` / `frozen_qty` —— 必须从建单那一刻冻结，否则盘点过程中库存还在变，差异就算不准了。
- `actual_qty` **NULL 表示尚未盘点**（不能用 0，0 是"盘出来确实是 0"）。`diff_qty = actual_qty - system_qty`。
- 过账后 `gain_qty`（盘盈）/ `loss_qty`（盘亏）汇总到单头，`post_time` 记录过账时间。
- 状态：`COUNTING → COMPLETED / CANCELLED`。

### 4.5 `transfer_order` + `transfer_order_item` —— 移库单（V1.0.7）

- 单头：`from_location_id` → `to_location_id`，同一仓库内。
- 明细唯一键 `(order_id, sku_id, batch_no)`，CHECK `qty > 0`。
- 状态：`CREATED → COMPLETED / CANCELLED`。
- 与 `stock_task` 的 `TRANSFER` 类型呼应。

## 5. 第四层：执行

### 5.1 `stock_task` —— 作业任务

把单据拆成"人能执行的动作"。

- `task_type`：`PUTAWAY` 上架 / `PICK` 拣货 / `TRANSFER` 移库 / `COUNT` 盘点。
- 来源三元组 `source_type` / `source_id` / `source_no` / `source_item_id`：能反查是哪张单据的哪条明细生成的。
- `from_location_id` / `to_location_id`：上架/移库用目标位，拣货用源库位。
- `priority` 越大越优先，`idx_status_priority (status, priority, create_time)` 支撑"待办任务池"排序。
- `deadline` + `idx_deadline (status, deadline)`：超时扫描。
- `retry_count` 重试次数。
- 状态：`CREATED → ASSIGNED → PROCESSING → DONE`，异常分支 `CANCELLED` / `TIMEOUT` / `EXCEPTION`。

## 6. 第五层：支撑表

### 6.1 `sys_sequence` —— 单号发号器（V1.0.1）

主键 `(biz_type, biz_date)`，`biz_date` 是 `yyyMMdd`，**每天从 1 重新开始**。

核心就一句：
```sql
INSERT ... ON DUPLICATE KEY UPDATE current_value = current_value + 1
```

**为什么不用 `MAX(order_no) + 1`**：两个请求同时查到 0005，会同时生成 0006，靠 `uk_order_no` 只能让其中一个报错 —— 并发一高用户就"偶尔创建失败"。
**为什么不用 Redis INCR**：发号这种小事不值得多一个故障点（写脚本时 Redis 还没引入）。
**为什么它天然不重号**：InnoDB 对这一行加排他锁，并发请求自动排队。

### 6.2 `idempotent_record` —— 幂等记录

- `idempotent_key` 唯一，形如 `OUTBOUND_ALLOC:OUT20260911000001`。
- `status`：0 处理中 / 1 成功 / 2 失败。
- `result_snapshot`：成功响应快照，**用于重放**（重复请求直接返回上次结果，而不是报错）。
- `request_hash`：检测"同一个 key 但参数不同"的异常调用。
- V1.0.2 补 `error_msg`：失败也要留原因，且不混进 `result_snapshot`（那个字段语义是"可重放的成功响应"，混进去就没法信任了）。
- V1.0.3 补 `locked_until`（**租约**）——这是个真实坑：
  > 抢位记录必须独立提交（否则别的线程看不到它，去重失效），于是"抢完位还没销登记"这段窗口不受事务保护。进程在这时挂了，记录就永远停在 status=0，之后所有同 key 请求都被拦住 —— 用户什么都没做成，系统却一直说"请勿重复提交"。

  修法：抢位时写 `locked_until = now + 30s`；后来者看租约，没过期 → 拒绝，已过期 → CAS 接手重试。索引 `(status, locked_until)` 给兜底扫描任务用（等值列在前，范围列在后）。

### 6.3 `audit_log` —— 审计日志

`trace_id` 串起一次请求的全链路；`module` / `action` / `target_type` / `target_id` 定位操作对象；`detail` 是 JSON 变更详情；还有 `ip`、`result`、`error_msg`、`cost_ms`。
索引设计覆盖了三种查法：按链路查、按人查、按模块查。

## 7. 两条核心链路（把这些串起来讲，面试很加分）

### 入库
```
创建入库单(inbound_order, CREATED)
  → 开始收货(RECEIVING) → 逐行收完(RECEIVED)  [写 received_qty]
  → 生成上架任务(stock_task, PUTAWAY)
  → 执行上架：inventory.qty += N，location.used_capacity += N
     + 落一条 inventory_transaction(qty_change=+N, source=INBOUND_ORDER)
  → 上架完成(PUTAWAY_DONE) → 关单(CLOSED)
```

### 出库
```
创建出库单(outbound_order, CREATED)
  → 分配库存：按 FIFO 挑 inventory，写 outbound_allocate(LOCKED)
             同时 inventory.locked_qty += N，记录 allocate_time
  → 全部分配完(ALLOCATED) → 生成拣货任务(stock_task, PICK)
  → 拣货(PICKING → PICKED)：inventory.locked_qty -= N, qty -= N
                            + 落 inventory_transaction(qty_change=-N)
  → 发运(SHIPPED) → 关单(CLOSED)
  → 【超时未拣】定时任务扫 idx_allocate_time，把 allocate 置 RELEASED，locked_qty 回滚
  → 【发运后要撤销】不回退，开红冲单（reverse_of_id 指回原单）
```

## 8. 面试可以直接讲的 8 个设计点

1. **库存四量模型** `qty / locked / frozen / available` + 生成列，从数据库层面杜绝数量不一致。
2. **乐观锁 `version`** 应对并发扣减，比 `SELECT FOR UPDATE` 吞吐高。
3. **流水表只增不改** + `tx_no` 唯一做幂等，保证每一笔变动可追溯、可重放。
4. **单据 + 快照双写**：id 用于关联统计，名称快照固化历史，改主数据不影响历史单据。
5. **发号器用 DB 行锁**而非 `MAX+1` 或 Redis，用最小代价解决并发重号。
6. **幂等租约 `locked_until`**：识别"进程死了留下的僵尸锁"，这是比单纯加锁更进一步的思考。
7. **红冲而非回退**：已发货单据不可撤销，用反向单构成完整凭证链（财务思维）。
8. **逻辑删除与唯一索引的冲突**：`deleted` 不进唯一键，所以编码不可复用 —— 能说出这个权衡说明真做过。

## 9. 速查表

> **逐字段明细见 `08-表字段速查手册.md`**（21 张表全字段 + 索引约束 + 枚举值汇总 + 单号规则）。
> 本表只用于快速回忆"这张表是干嘛的"。

| 表 | 作用 | 关键点 |
|---|---|---|
| `sys_user` | 系统用户 | BCrypt，3 角色 |
| `warehouse` | 仓库 | 顶级容器 |
| `zone` | 库区 | 仓库内唯一，4 类型 |
| `location` | 库位 | 库存挂载点，冗余容量 |
| `product` | 商品 SKU | 尺寸/重量/保质期 |
| `partner` | 供应商+客户 | 合成一张表，V1.0.4 |
| `inventory` | 库存余额 | 四量 + 生成列 + 乐观锁 |
| `inventory_transaction` | 库存流水 | 只增不改，tx_no 幂等 |
| `inbound_order`(+item) | 入库单 | 收货≠上架 |
| `outbound_order`(+item) | 出库单 | 红冲，超时释放 |
| `outbound_allocate` | 分配明细 | 锁定的载体 |
| `stocktaking_order`(+item) | 盘点单 | 建单时冻结系统量 |
| `transfer_order`(+item) | 移库单 | 库位到库位 |
| `stock_task` | 作业任务 | 4 类型 7 状态 |
| `sys_sequence` | 发号器 | 行锁自增，按天重置 |
| `idempotent_record` | 幂等记录 | 租约 + 结果快照 |
| `audit_log` | 审计日志 | trace_id 全链路 |

单号规则：`IN+yyyMMdd+6位` / `OUT+...` / `TASK+...` / `ST+...` / `TR+...`
