# 05 · 库存作业设计与实现（冻结 / 移库 / 盘点 / 对账）

这一篇讲的是「不动出入库单据，直接对库存动手」的四类作业。
前三个（冻结 / 移库 / 盘点）是**业务动作**，第四个（对账）是**数据自检与修复**。

它们全都建立在同一个前提上：**库存只有一个写入口**（`InventoryService.applyChange`），
本模块的所有代码都不自己 `UPDATE inventory`（唯一破例的是对账修正，下文 2.7 专门讲为什么）。

---

## 1. 链路全景

### 1.1 四种动作各改什么

| 动作 | qty | locked_qty | frozen_qty | 流水类型 | 能逆吗 |
|---|---|---|---|---|---|
| 冻结 | 0 | 0 | **+n** | `FREEZE` | 能（解冻） |
| 解冻 | 0 | 0 | **−n** | `UNFREEZE` | —— |
| 移库转出 | **−n** | 0 | 0 | `TRANSFER_OUT` | 能（再移回来） |
| 移库转入 | **+n** | 0 | 0 | `TRANSFER_IN` | —— |
| 盘盈 | **+diff** | 0 | 0 | `STOCKTAKING_GAIN` | 能（再盘一次） |
| 盘亏 | **−diff** | 0 | 0 | `STOCKTAKING_LOSS` | 能（再盘一次） |
| 对账修正 | 按流水重算 | 按流水重算 | 按流水重算 | **不写流水** | —— |

这张表是理解本模块的钥匙：

- **冻结只动 `frozen_qty`**：货还在库里（`qty` 不变），只是可用数量变少。所以它是一个**完全可逆**的操作。
- **移库改两条库存行的 `qty`**：一次作业在账上是两笔变动，一减一加。
- **盘点改 `qty`**：盘盈相当于「凭空多出来的货入账」，盘亏相当于「少掉的货出账」。
- **对账不改业务数量，只是把余额重算一遍**。

任何动作之后都必须满足（`applyChange` 里的不变量校验）：

```
qty >= 0、locked_qty >= 0、frozen_qty >= 0
locked_qty + frozen_qty <= qty      （也就是 available_qty >= 0）
```

### 1.2 分层：业务动作 → 写入内核 → SQL

```
InventoryAdjustServiceImpl          业务动作层：校验业务规则、拼装 command
        │   （冻结 / 移库 / 盘点 / 对账）
        ▼
InventoryService.applyChange        写入内核：ensureRow → 锁行 → 先算后校验 → CAS → 写流水
        │
        ▼
InventoryMapper / XML               SQL 层
```

为什么分成两层？

- 内核（`applyChange`）**不知道什么是移库、什么是盘点**。它只知道「在库 +n、冻结 −m」。
  它要解决的问题永远只有一个：**这次变动怎么安全地落到库里并且留下流水**。
- 业务层负责「什么算合法」：目标库位启用了吗？解冻量超过冻结量了吗？移出移入是同一个库位吗？

这样分层的结果是：以后加「质检冻结」「报废出库」「库位整理」这类新动作，
**只需要在业务层加一个方法**，锁、CAS、流水、不变量校验全都自动继承。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/inventory/inventories` | 库存分页 |
| GET | `/api/v1/inventory/inventories/{id}` | 库存详情（移库 / 盘点深链入口） |
| POST | `/api/v1/inventory/inventories/{id}/freeze` | 冻结，body `{ qty }` |
| POST | `/api/v1/inventory/inventories/{id}/unfreeze` | 解冻，body `{ qty }` |

| POST | `/api/v1/inventory/stocktakings` | 盘点，body `{ locationId, skuId, batchNo, actualQty, remark }` |
| GET / POST | `/api/v1/inventory/stocktaking-orders` | 盘点单分页 / 按库位快照建单 |
| GET | `/api/v1/inventory/stocktaking-orders/{id}` | 盘点单详情 |

URL 全是**动作型**的，没有 `PUT /inventories/{id}`。

原因：库存不是一个可以随手编辑的字段。想改库存，就必须说清楚「是什么业务原因」——
冻结是冻结、盘亏是盘亏，每种原因对应一种流水类型。
一旦开了「直接改数」的口子，BR-008（每次变动必写流水）就守不住了，
而且出了账实不符的问题也查不出是谁用什么理由改的。

## 2. 关键设计

### 2.1 冻结：只挪「可用」，不动「在库」

```java
inventoryService.applyChange(baseCommand(inventory)
        .frozenChange(qty)              // 只动冻结
        .txType(InventoryTxType.FREEZE)
        .build());
```

库存行 `qty=100` 冻结 30 之后：

```
qty = 100        货还在库里，一件没少
frozen_qty = 30
available_qty = 70      ← MySQL 生成列算出来的
```

**这个设计的意义是「锁住但不拿走」。** 现实里的场景是货物有争议、质量待判、
客户已下单但还没发货 —— 这些货物理上都在，只是不能动。

`available_qty` 是生成列（`qty - locked_qty - frozen_qty`），
所以冻结之后**不需要任何额外代码**，出库分配（`available_qty > 0`）和移库
（校验 `available >= qty`）就会自动避开被冻结的部分。这就是 BR-005 的实现方式：
**不是在各处写 if 判断，而是让不可用的数量在数据层面就不可见。**

### 2.2 移库：一个事务里的两次 `applyChange`

移库是本模块最容易写错的地方。它一次要改**两条**库存行：

```java
// ① 转出：源库位 qty -qty（createIfAbsent = false）
inventoryService.applyChange(…… qtyChange(-qty)  TRANSFER_OUT  createIfAbsent(false));

// ② 转入：目标库位 qty +qty（createIfAbsent = true）
inventoryService.applyChange(…… qtyChange(+qty)  TRANSFER_IN   createIfAbsent(true));
```

**为什么必须在一个事务里**：两条都成功才叫移库，只成功一条就是「货从 A 走了但没到 B」——
库存凭空消失，比移库失败严重得多。

实现方式是 `transfer()` 上加 `@Transactional`：`applyChange` 是另一个 Bean，
事务传播是 `REQUIRED`，所以两次调用**并入同一个事务**，第二条失败时第一条一起回滚。

> 小知识：这里能靠事务传播解决，是因为 `applyChange` 在**别的 Bean** 上。
> 如果移库逻辑写在 `InventoryServiceImpl` 内部、直接调 `this.applyChange(...)`，
> 那就不走 Spring 代理，`@Transactional` 会失效 —— 这是 docs/02 里提过的「自调用陷阱」。

**为什么转入侧要 `createIfAbsent = true`**：目标库位以前可能从来没放过这个批次，
不自动建行就没法加锁（锁不存在的行是无效的）。而转出侧必须为 `false`：
货本来就在源库位，源库存行不存在说明是数据异常，应该报错而不是造一条 0 库存出来。

**为什么要校验目标库位**：

| 校验 | 原因 |
|---|---|
| 目标库位存在且 `status = ENABLED` | 停用 / 冻结的库位上不允许再放货 |
| 目标库位与源库位同仓库 | 跨仓库搬货中间有运输在途，那叫调拨，要走出库 + 入库单据 |
| 源库存 `available_qty >= qty` | 被订单锁定、被冻结的货挪不动（BR-005） |

**生产日期 / 到期日期要跟着一起搬过来**：转入时把源批次的 `productionDate` / `expiryDate`
带进 command。不带的话目标库位那一行就没有效期，临期预警会直接漏掉这批货 ——
同一个批次换个位置，不该变成另一种精度。

### 2.3 库位占用：任何「减少库存」的动作都要同步减

`location.used_capacity` 是给看板看的冗余计数（库位占用率、超容预警都靠它）。
移库是**唯一一个「同一时刻既减又加」**的场景，所以必须成对调整：

```java
locationService.decreaseUsedCapacity(source.getLocationId(), qty);
locationService.increaseUsedCapacity(dto.getToLocationId(), qty);
```

只加不减的话，每移一次库「已用容量」就凭空多一份，看板的占用率会越来越离谱。

两个方法的脾气不一样，这是刻意的：

| 方法 | 计数不够时 | 为什么 |
|---|---|---|
| `increaseUsedCapacity` | **抛异常**（库位容量不足，BR-006） | 放不下就是放不下，不能装作放得下 |
| `decreaseUsedCapacity` | **返回 false + 打日志** | 计数只是派生数据，它自己算错了不该把移库这种正经业务卡死 |

**一句话记住这个派生计数的口径：任何「减少库存」的动作都必须同步减库位占用。**

| 动作 | 库位占用 | 代码位置 |
|---|---|---|
| 上架入库 | +qty | `StockTaskServiceImpl.complete` |
| 移库 | 源 −qty、目标 +qty | `InventoryAdjustServiceImpl.transfer` |
| 盘盈 / 盘亏 | +diff / −diff | `InventoryAdjustServiceImpl.stocktake` |
| 出库发货 | **−qty** | `OutboundOrderServiceImpl.ship` |

不变量：**`location.used_capacity` 应该等于这个库位上所有库存行的 `qty` 之和。**

> **踩坑（真实发生）**：出库发货的第一版只减了 `inventory.qty`，忘了减 `used_capacity`。
> 结果每发一次货，库位就「少」一点容量，占用率只增不减，最后空库位也会报容量不足。
>
> 发现方式不是读代码，是看真实数据：某个库位记录占用 90，而它上面只有 45 件货。
> 修的时候补了一条回归用例，并且**把修复那行注掉验了一次**，确认它会红
> （`expected: 1070 but was: 1110`，正好差发出去的 40 件）——
> 用例能抓住 bug，才算真的防住了它，否则只是「看起来有测试」。
>
> 任何派生计数都该配一条自检 SQL：
> ```sql
> SELECT l.id, l.code, l.used_capacity, COALESCE(SUM(i.qty), 0) AS real_qty
> FROM location l
>          LEFT JOIN inventory i ON i.location_id = l.id AND i.deleted = 0
> WHERE l.deleted = 0
> GROUP BY l.id, l.code, l.used_capacity
> HAVING l.used_capacity <> COALESCE(SUM(i.qty), 0);
> ```
> 顺手用它修了库里两条历史脏数据：A-01-01-02 从 90 改成 45、A-01-02-01 从 100 改成 95。

### 2.4 盘点：前端传「实盘数量」，差异由后端算

```java
int diff = actualQty - systemQty;
diff > 0  → STOCKTAKING_GAIN（盘盈）  qtyChange(+diff)
diff < 0  → STOCKTAKING_LOSS（盘亏）  qtyChange(-diff)
diff == 0 → 什么都不做
```

**为什么不让人传差异**：传差异意味着前端得先知道系统数量（多一次往返），
而且给了前端算错 / 造假的机会。盘点的全部意义就是「数了多少就是多少」，
所以 API 收的是**实盘数量**这个原始事实，差异是服务端算出来的结论。

前端仍然会实时显示差异（`diff = 实盘 − 系统`）—— 但那是**给操作人看的即时反馈**，
不是提交上去的数据。这个区别很重要：**能算给用户看 ≠ 该让用户传**。

允许 `actualQty = 0`（盘点发现一件不剩是合法结果），
但如果盘亏之后 `locked + frozen > qty`，`applyChange` 的不变量校验会拒绝：

```
库存 100，其中 30 件已被出库单锁定 → 实盘填 20
qty=20 而 locked=30 → 可用数量为负 → 拒绝
```

物理上不可能发生的事（货被订单占着，实物却一件都没有），必须在数据层挡住。

### 2.5 盘点为什么「账实相符」不写流水

`diff == 0` 时直接返回，**不写任何流水**。

理由：流水记的是**发生过的变动**。0 变动没有信息量，写进去只会：

1. 让流水表变脏 —— 全表是「什么都没发生」的噪音
2. 让对账变慢 —— 对账要 `SUM(qty_change)`，多一堆 0 毫无意义
3. 让审计失真 —— 以后看流水会以为那一刻库存动过

「什么时候盘过、谁盘的」这类**作业痕迹**属于盘点单 / 盘点任务该记的事，
不是库存流水该记的事。两张表职责不同，不要混。

### 2.6 对账：余额是缓存，流水是账本

BR-009：**库存余额必须能由流水重算，不一致时以流水为准并告警。**

```
inventory.qty            余额快照（可以被改坏的缓存）
inventory_transaction    流水账本（只增不改不删）
```

`SUM(qty_change)` 按 `(库位, SKU, 批次)` 分组累加，就应该是 `inventory.qty`。
对账 SQL 一条就能查出所有不平的行：

```sql
SELECT i.id, i.qty AS balance_qty, COALESCE(t.calc_qty, 0) AS calculated_qty
FROM inventory i
LEFT JOIN (SELECT location_id, sku_id, batch_no,
                  SUM(qty_change)    AS calc_qty,
                  SUM(locked_change) AS calc_locked,
                  SUM(frozen_change) AS calc_frozen
           FROM inventory_transaction
           GROUP BY location_id, sku_id, batch_no) t
       ON t.location_id = i.location_id AND t.sku_id = i.sku_id AND t.batch_no = i.batch_no
WHERE i.deleted = 0
  AND (i.qty        <> COALESCE(t.calc_qty, 0)
    OR i.locked_qty <> COALESCE(t.calc_locked, 0)
    OR i.frozen_qty <> COALESCE(t.calc_frozen, 0))
```

三个细节都是有原因的：

1. **`COALESCE(..., 0)` 不能省**：`LEFT JOIN` 之后没有流水的行算出来是 `NULL`，
   而 `NULL` 参与任何比较结果都是 `NULL` —— 这行会被静默漏掉，也就是说
   「有人手工插了一条库存但没有流水」这种最该报警的情况反而查不出来。
2. **三个量一起比**：只比 `qty` 的话，「货没少但锁定数丢了」这种问题查不出来。
3. **用 `qty_change` 而不是 `qty_after`**：`qty_after` 是变动那一刻的快照，
   只有连续读到全部流水时才有意义；累加**变动量**才是和当前余额可比的量。

**为什么以流水为准**：流水只增不改不删，改不了；余额随时可以被静默改掉。
缓存和它的来源不一致时，相信来源。

**修正动作是「重算派生值」，所以不写流水** —— 这条结论有故事，见下一节。

### 2.7 ★ 对账修正为什么不能写库存流水（踩坑记录）

一开始的设计是「所有写库存都必须走 `applyChange`，所以修正也走它」，
这样规则最统一、没有例外。**写测试的时候发现它不收敛**：

```
流水 SUM = 150            （PUTAWAY_IN +100、+50）
余额被手工改坏成 999
走 applyChange 修正 → 写一条 qty_change = 999 - 150 → -849 的流水
修正后：余额 = 150 ✔    但流水 SUM = 150 - 849 = -699 ✘
下一次对账继续报不平，再修一次又差 849 …… 永远平不了
```

根因是**语义搞混了**：

- `applyChange` 记的是「库存变动」—— 有货真的进出仓库。
- 对账修正记的是「把一个可以推导出来的值重算了一遍」—— **没有任何货动**。

把一个「重算」写进账本，等于往账本里塞了一笔假变动，账本自己就被污染了。

所以最终实现是：**直接改余额，但不写库存流水**。

```java
inventoryMapper.repairBalance(id, qty, lockedQty, frozenQty, version);   // 带 version 做 CAS
log.warn("对账修正 inventoryId={} 余额 {} -> {}（以流水为准）", ...);
```

这是全项目**唯一一处绕过 `applyChange` 直接写 inventory 的地方**，
所以它在代码里被写得非常啰嗦（Mapper 接口、XML、Service 三处都写了为什么）。
需要正式审计痕迹时应该写 `audit_log`（谁在什么时候重算了哪一行），
而不是写 `inventory_transaction`。

**这个坑的价值**：它说明「规则统一」不能压倒「语义正确」。
真正需要守住的不变量是「账本能推出余额」，而不是「所有 SQL 都长一个样」。

### 2.8 对账修正为什么要带 `version` 做 CAS

对账是「先扫一遍，再挨个修」。从扫到修之间，这一行可能被正常业务改过
（有人上架、有人发货）。这时候如果直接 `UPDATE`，就会**覆盖掉别人刚做的正常变动**。

所以修正 SQL 带上扫描时读到的 `version`：

```sql
UPDATE inventory
SET qty = #{qty}, locked_qty = #{lockedQty}, frozen_qty = #{frozenQty}, version = version + 1
WHERE id = #{id} AND version = #{version} AND deleted = 0
```

影响行数 0 就说明「期间被改过」，这次修正作废，记成 `FAILED`，
下一次对账会重新发现它。**宁可少修一次，也不要覆盖别人。**

### 2.9 对账为什么不加 `@Transactional`

对账要一次扫很多行、挨个修。如果整批一个事务，第 8 行修不动（比如按流水算出来的数量
不满足 `locked + frozen <= qty`，说明流水本身也烂了）就会把前 7 行的成功修正**一起回滚**。

一个「修账工具」应该是**能修多少修多少**。所以 `reconcile()` 刻意不开事务，
每次 `repairBalance` 都是一条独立的、自带 CAS 的语句。

同理，单行修正失败时只记 `fixResult = FAILED` + 原因，继续修后面的行 ——
一条烂数据不该让整次对账作废。

### 2.10 错误码：为什么「解冻超量」要单独一个码

解冻 20 但只冻了 10，如果任由 `applyChange` 去报错，用户看到的是
「可用库存不足」（60003，`locked + frozen > qty`）—— **对用户完全是误导**：
可用为什么不足？我明明是在解冻。

所以业务层先检查、抛出专门的 `FREEZE_NOT_ENOUGH(50010, "可解冻数量不足")`：

> **核心规则用通用错误码兜底，业务层用具体错误码解释。**
> 用户看到的报错要能直接指出「哪里不对」，而不是让他去猜。

### 2.11 出库类方向一律 `createIfAbsent = false`

`InventoryChangeCommand.createIfAbsent` 是一个开关：

| 方向 | 取值 | 理由 |
|---|---|---|
| 入库上架 / 移库转入 | `true` | 第一次进这个库位，需要先建行才能加锁 |
| 冻结 / 解冻 / 移库转出 / 盘点 / 对账修正 | `false` | 行不存在说明「这个库位本来就没这批货」，应该报错 |

否则会出现这种荒唐事：盘一个从来没放过货的库位，系统先给它建一条 0 库存记录，
再报「实盘数量不能小于 0」—— 数据脏了，问题还没解决。

## 3. 错误码

| 码 | 常量 | 含义 |
|---|---|---|
| 50001 | `STOCK_NOT_ENOUGH` | 库存不足（会扣成负数） |
| 50002 | `STOCK_NOT_FOUND` | 库存记录不存在 |
| 50005 | `INVENTORY_CONCURRENT_MODIFY` | 库存被并发修改（CAS 失败 / 修正期间被改） |
| 50006 | `INVALID_QTY_CHANGE` | 三个变动量全为 0 |
| 50007 | `INVALID_ADJUST_QTY` | 调整数量必须大于 0 |
| 50008 | `TRANSFER_SAME_LOCATION` | 移出和移入填了同一个库位 |
| 50009 | `LOCATION_DISABLED` | 目标库位已停用或冻结 |
| 50010 | `FREEZE_NOT_ENOUGH` | 可解冻数量不足 |
| 50011 | `TRANSFER_CROSS_WAREHOUSE` | 只能在同一仓库内移库 |
| 60003 | `AVAILABLE_NOT_ENOUGH` | 可用库存不足（不变量校验） |
| 30009 | `LOCATION_CAPACITY_NOT_ENOUGH` | 库位容量不足（BR-006，来自基础数据模块） |

## 4. 测试清单

`InventoryAdjustServiceTest`（17 个用例），跑之前**自建独立仓库 / 库位 / 商品**，
`@AfterEach` 物理清理 —— 这类测试会直接改数据库（造假数据给对账去发现），
碰上真实数据就不再可重复，还会污染别人。

**这个测试类不能用 `@Transactional`**：最有价值的两个验证点就是「事务回滚」和「对账修正」，
测试自己开着事务会把它们包住，回滚根本验证不出来。

| 用例 | 验证什么 |
|---|---|
| 冻结 / 解冻 | `frozen_qty` 增减，`qty` 不变，`available_qty` 由生成列正确推导 |
| 冻结超过可用 | 报 60003，且**库存和流水都没变** |
| 解冻超过冻结量 | 报 50010（不是含糊的库存不足），库存没变 |
| ★ 冻结的货不能移库 | BR-005：全部冻结后移库被可用数量挡住 |
| ★ 移库成功 | 源 −30 / 目标 +30、总量守恒、两条流水、目标行自动创建、库位占用一减一加 |
| 移库带效期 | 目标库位那一行拿到源批次的 `production_date` / `expiry_date` |
| 移库到同一库位 / 停用库位 | 50008 / 50009，库存不变 |
| ★ 移库的原子性 | 目标库位容量不足时，**转出的库存和库位占用一起回滚**，只留下入库那一条流水 |
| 盘盈 / 盘亏 | 差异签名、流水类型、库存数量 |
| 账实相符 | `changed = false`，**不写流水** |
| ★ 盘亏不能盘掉被锁定的货 | 实盘 < `locked + frozen` 时拒绝 |
| 盘不存在的库存行 | 报 50002，且不会自动建行 |
| ★ 对账检出 + 修正 + 再对账 | 改坏的余额被扫出来 → 修正 → **再对一次是平的**（收敛性） |
| 对账也检查锁定 / 冻结 | 不只是比 `qty` |

其中「对账收敛性」那条用例就是发现 2.7 那个坑的地方：
第一版实现里它是红的，正是它逼出了「修正不能写流水」这个结论。

## 5. 遗留与后续

1. **`location.used_capacity` 这个派生计数还没有并入对账任务**。
   它和库存是双写（上架 / 发货 / 移库 / 盘点各写一次），已经漏减过一次（见 2.3）。
   现在只有一条手工跑的自检 SQL；正规做法是把它并进对账任务一起扫，
   不一致就告警 —— 口径同样以库存为准，因为库存才是业务数据，占用只是它的投影。
2. **对账是全表扫**。当前直接对 `inventory_transaction` 全表分组，学习项目的数据量没问题；
   生产上流水表要按时间分区、只在低峰跑。它的优点是不平的行才返回，
   正常情况下一条都不返回，所以可以随时跑。
3. **对账的审计痕迹只有应用日志**。
   更正式的做法是写 `audit_log`（表已经建好，但还没有对应代码）：
   谁、什么时候、把哪一行从多少改成了多少。
4. **基础盘点单 / 移库单已补齐**。盘点单会快照库位库存、分批录入并校验快照后过账；
   移库单支持多 SKU / 批次并保留单据来源流水。下一步可以继续加库位锁定、复核/审批流和盘点任务。
5. **移库单目前仍是“建单后手工确认执行”**。尚未接拣货补货、上架推荐等自动生成规则；
   真做自动补货时，移库单可以作为下游单据直接接收来源 `source_type/source_id`。
