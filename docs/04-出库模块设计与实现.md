# 04 · 出库模块设计与实现

出库链路（建单 → 分配 → 拣货 → 发货）的关键设计。承接 `03-入库模块设计与实现.md` 的思路，
每条按「问题 → 方案 → 为什么 → 面试怎么讲」组织。

## 1. 链路全景

### 1.1 状态机

```
CREATED ──分配──> ALLOCATED ──开始拣货──> PICKING ──拣完──> PICKED ──发货──> SHIPPED ──> CLOSED
   │                  │
   └──取消──> CANCELLED └──释放/超时──> CREATED
```

**注意 `ALLOCATED → CREATED` 这条回退边，以及 `PICKING` 之后不能再回退**：
货一旦从货架上拿下来，释放分配就会造成账实不符，只能往前走。

### 1.2 ★ 三步库存模型

这是整个出库模块最重要的一条设计：

| 阶段 | `qty` | `locked_qty` | 说明 |
|---|---|---|---|
| **分配** | 不变 | **+n** | 货还在货架上，账上先占住 |
| **拣货** | 不变 | 不变 | 货在推车上，账面先不动 |
| **发货** | **−n** | **−n** | 账实核销，唯一不可逆的一步 |

`available_qty = qty - locked - frozen`，三个阶段的变化：

```
分配前：qty=50  locked=0   available=50
分配后：qty=50  locked=10  available=40    ← 只锁，不动 qty
拣货后：qty=50  locked=10  available=40    ← 完全不动
发货后：qty=40  locked=0   available=40    ← 一起减，可用量保持不变
```

**为什么拣货不改库存？**

拣货可能失败：破损、找不到货、复核时发现数量不对。如果拣货时就把账扣了，
这些情况全都要写补偿逻辑把库存加回去。

**把不可逆的操作推到最后** —— 和入库那边「收货不改库存、上架才改」是同一个思路。

**面试怎么讲**：

> 「出库我用了三步库存模型：分配只锁 locked_qty，拣货什么都不动，发货才 qty 和 locked 一起减。
> 因为拣货可能失败，那时候如果账已经扣了就得写补偿。把不可逆的核销推到最后一步，
> 前面的动作全都是可回滚的。这和入库的『收货不增加库存、上架才增加』是一个思路。」

## 2. 关键设计

### 2.1 FIFO 分配（BR-004）

**规则**：优先入库早的批次，其次生产日期早的批次；一批不够就拆到下一批。

```sql
SELECT ... FROM inventory
WHERE deleted = 0
  AND warehouse_id = ? AND sku_id = ?
  AND available_qty > 0                      -- 走 idx_available 索引
ORDER BY inbound_time ASC, production_date ASC, id ASC
```

**为什么最后要跟一个 `id ASC`**：排序必须有确定性。不加兜底字段时，
`inbound_time` 和 `production_date` 完全相同的两条记录，MySQL 返回顺序是不保证的，
并发分配可能因此以不同顺序加锁 → **死锁**。

分配逻辑：

```java
for (OutboundOrderItem item : items) {
    int need = item.getQty();
    for (Inventory candidate : fifoAvailable) {
        int take = min(need, candidate.available);
        inventoryService.applyChange(lockedChange = +take, ALLOCATE_LOCK);
        allocateMapper.insert(...);            // 一条分配明细
        need -= take;
    }
    if (need > 0) throw STOCK_NOT_ENOUGH_FOR_ALLOCATE;   // 整单回滚
}
```

一条出库明细可能对应**多条**分配明细，这就是 FIFO 按批次拆分的产物。

### 2.2 乐观读 + 悲观写 + 写时重新校验

分配的第一步是**普通查询**（不加锁）拿到候选批次，看起来有并发问题：

```
A: 查到 B 批次可用 50
B: 查到 B 批次可用 50        ← 两个都通过了读
A: 锁定 50
B: 锁定 50                   ← 超卖！
```

**为什么不会超卖**：候选查询只是"候选"，真正锁定走的是 `applyChange`：

```java
applyChange(lockedChange = +take)   // 内部：SELECT ... FOR UPDATE + 重新校验可用量
```

它加行锁、重新算 `locked + frozen <= qty`，不满足直接抛 `60003`，整个分配事务回滚。

这是「**乐观读 + 悲观写 + 写时重新校验**」的经典组合：
读的时候不阻塞别人（吞吐高），写的时候用锁和校验兜底（不会错）。

**实测**（`OutboundRollbackTest.concurrentAllocateShouldNotOversell`）：
100 件库存，3 张单并发各要 50 件 → **正好 2 张成功、1 张被拒，锁定量恰好 100**。

### 2.3 整单原子

任一明细分配不满，**整单回滚**，之前锁上的库存全部还回去。

```java
if (need > 0) {
    throw new BizException(STOCK_NOT_ENOUGH_FOR_ALLOCATE);
    // 方法上有 @Transactional，前面 applyChange 加的 locked_qty 和流水一起回滚
}
```

为什么不做"部分分配"？因为出库单是给客户的承诺，
分配一半意味着"只能发一半货"，业务上不如整单失败让人重新决策清晰。

> **测试注意**：这个原子性在 `@Transactional` 的测试类里验不出来 ——
> 测试事务和 Service 事务是同一个，异常只是把事务标记成 rollback-only，
> 回滚发生在测试结束，断言时数据还在。必须放到**非事务**的测试类里验。

### 2.4 出库不能凭空创建库存行

入库是 `createIfAbsent = true`：第一次上架时这个「库位+SKU+批次」还没有库存，
需要先建行才能加锁（锁不存在的行是无效的）。

出库必须传 `createIfAbsent = false`：

```java
InventoryChangeCommand.builder()
    .lockedChange(take)
    .createIfAbsent(false)      // ← 没库存就是没库存
```

否则「分配」这个动作会先 INSERT 一条 0 库存的记录，再因为校验不过而失败 ——
**在库存表里留下一堆垃圾行**。

### 2.5 拣货任务按分配明细生成

一条拣货任务 = 一条分配明细 = 一个库位的一个批次。

```
出库单明细：SKU0001 × 40
   ├─ 分配明细 1：A-01-01-02 / B-OUT-1 / 30 件  →  拣货任务 1（30 件）
   └─ 分配明细 2：A-01-01-02 / B-OUT-2 / 10 件  →  拣货任务 2（10 件）
```

**为什么不是一条任务拣两个批次**：作业员必须知道"去哪个库位拿多少"，
按库位拆开才可执行。拣完货系统才知道要从哪几个批次核销。

`stock_task.source_item_id` 存的是**分配明细 id**，拣货完成时靠它回写。

### 2.6 拣货完成不碰库存

`StockTaskService.complete()` 按任务类型分流：

```java
if (TaskType.PICK.name().equals(task.getTaskType())) {
    completePick(task, actualQty);      // 只回写出库单，一行库存代码都没有
} else {
    completePutaway(task, actualQty);   // 上架：写库存 + 占容量 + 回写入库单
}
```

**这是刻意的**。如果 `completePick` 里也去调 `applyChange`，三步模型就塌了。

### 2.7 状态流转：什么时候加锁，什么时候一条 CAS 就够

| 场景 | 做法 | 为什么 |
|---|---|---|
| **分配** | `SELECT ... FOR UPDATE` 锁单据行 | 要读明细、算总量、写回，中间不能插队 |
| **释放** | 锁单据行 + 检查未完成任务 | 一样要先读后写 |
| **发货** | 锁单据行 | 要读分配明细再逐条核销 |
| **取消** | 一条带 `status` 条件的 UPDATE | 不需要读原始数据，SQL 本身就是原子的 |

判断标准还是那句：**要不要先读后写**。

### 2.8 释放分配前必须检查在途任务

```java
if (orderMapper.countUnfinishedPickTask(orderId) > 0) {
    throw new BizException(PICK_TASK_UNFINISHED);   // 60005
}
```

否则会出现：库存锁定已经还回去了，作业员手里还拿着老任务去拣货 —— 货架上的货已经被别人分配走了。

> 「读 `stock_task` 的只读 COUNT」放在 outbound 模块自己的 Mapper 里。
> 跨模块不注入对方的 Mapper，但**只读投影**是可以接受的（和库位推荐同一个处理方式）。

### 2.9 依赖方向

```
task → outbound / inbound / inventory / basedata      （单向）
outbound → inventory / basedata                       （不反向依赖 task）
```

- **生成拣货任务**由 `StockTaskService` 实现，`OutboundOrderController` 直接委托它
- **拣货完成回调**由 task 调 `outboundOrderService.onPickCompleted(...)`
- 单据状态流转永远由 outbound 模块自己负责，别的模块只能"通知"

**怎么保证单向**：谁拥有数据谁负责状态。task 拥有任务表，outbound 拥有单据表。

## 3. 错误码

| code | 含义 | 触发场景 |
|---|---|---|
| 60001 | 出库单状态不允许该操作 | 重复分配、未拣完就发货 |
| 60003 | 可用库存不足，分配失败 | FIFO 分配时可用量不够 |
| 60005 | 存在未完成的拣货任务 | 释放分配时还有在途任务 |
| 60006 | 没有可拣货的分配记录 | 生成拣货任务时没有 LOCKED 记录 |
| 60007 | 分配记录状态不允许该操作 | 同一条分配被拣两次 |
| 50001 | 库存不足 | 出库变动时该库位没有这批货 |
| 60003 | 可用库存不足 | `applyChange` 重算可用量不够 |

## 4. 测试清单

`mvn test` 共 **50 个用例**（出库新增 12 个）。

| 测试类 | 用例 | 覆盖 |
|---|---|---|
| `OutboundOrderServiceTest` | 10 | 建单、FIFO 拆分、只锁量、释放、取消、拣货不动库存、发货核销 |
| `OutboundRollbackTest` | 2 | **整单原子回滚**、**并发分配不超卖** |

### 两个必测的并发/原子用例

```java
// 整单原子：库存 30 要 100 → 整单失败，locked_qty 必须回到 0
// 并发不超卖：库存 100，3 张单各要 50 并发分配 → 只能成功 2 张
```

> **测试隔离的坑**：FIFO 是按 `(仓库, SKU)` **全局**排序的。
> 如果测试用真实 SKU（比如 SKU0001），库里恰好存在同一 SKU 更早入库的批次，
> 分配就会先去拿它，断言全崩。
>
> 我在开发过程中就踩了这个 —— 测试一开始全绿（因为库是干净的），
> 等做了几次真实操作、库里有数据之后，5 个用例突然挂了。
>
> **正确做法**：测试自己造一个专用 SKU（`TEST-OUT-SKU`），保证 FIFO 候选里只有本用例的数据。

## 5. 踩坑记录

| # | 现象 | 根因 | 教训 |
|---|---|---|---|
| 1 | 测试全绿，几次真实操作后突然挂 5 个 | 测试用真实 SKU，FIFO 被库里已有批次干扰 | **测试必须自造数据**，不能依赖全局库状态 |
| 2 | `@Transactional` 测试里验不出"整单回滚" | 测试事务和 Service 事务是同一个，异常只标记 rollback-only，回滚在测试结束后才发生 | 验回滚/并发要放**非事务**测试类 |
| 3 | 拣货完成但单据没到 PICKED | 测试直接调 `onPickCompleted` 跳过了"生成拣货任务"这一步，单据还在 ALLOCATED | 写集成测试要走**真实调用链**，别跳步 |
| 4 | `markReleased` 里写了 `allocated_time` | 列名是 `allocate_time` | 自定义 SQL 的列名没有编译期检查，改完要跑一次 |
| 5 | 任务列表里拣货任务显示成"上架路径"、"完成上架" | 同一个列表组件硬编码了上架文案 | 复用一个组件时要把**差异抽成配置**（taskType） |
