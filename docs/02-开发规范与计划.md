# 02 · 开发规范与计划

## 1. 工程结构

单 Maven 模块，**按业务模块分包、模块内再分层**。第 1-9 周不要拆多模块。

```
wms-server/
├── pom.xml
└── src/main/
    ├── java/com/myproject/wmsserver/
    │   ├── WmsServerApplication.java
    │   ├── common/            全局公共
    │   │   ├── result/        Result<T>、PageResult<T>
    │   │   ├── exception/     BizException、ErrorCode、全局异常处理
    │   │   ├── context/       UserContext（ThreadLocal 存当前用户）
    │   │   └── util/
    │   ├── config/            MyBatisPlusConfig、WebMvcConfig、Knife4jConfig
    │   ├── web/               TraceIdFilter、JwtInterceptor
    │   ├── system/            模块：登录、用户
    │   ├── basedata/          模块：仓库 / 库区 / 库位 / 商品
    │   ├── inventory/         模块：库存、流水、移库、盘点
    │   ├── inbound/           模块：入库单、收货
    │   ├── putaway/           模块：上架任务、库位推荐
    │   ├── task/              模块：任务状态机
    │   ├── outbound/          模块：出库单、分配、发货
    │   └── picking/           模块：拣货
    └── resources/
        ├── application.yml
        ├── db/migration/      Flyway 迁移脚本
        └── mapper/            复杂 SQL 的 XML（简单 CRUD 不写）
```

每个业务模块内部：

```
basedata/
├── controller/   接口层
├── service/      业务逻辑（+ impl/）
├── mapper/       数据访问
├── entity/       表映射对象
├── dto/          入参
├── vo/           出参
└── enums/        该模块的枚举
```

## 2. 分层职责

| 层 | 职责 | 禁止 |
|---|---|---|
| Controller | 参数校验、调用 Service、返回 `Result<T>` | 写业务逻辑、注入 Mapper、开事务 |
| Service | 业务规则、事务边界、编排多个 Mapper | 处理 HTTP 对象 |
| Mapper | 数据访问，一条 SQL 一个方法 | 写业务判断 |
| Entity | 表结构映射 | 直接返回给前端 |
| DTO / VO | 入参 / 出参 | VO 泄露密码等敏感字段 |

**跨模块只能调对方的 Service，不能注入别人的 Mapper。**

### 对象命名

| 后缀 | 用途 | 例 |
|---|---|---|
| 无 | 数据库实体 | `Warehouse` |
| `SaveDTO` | 创建 / 更新的请求体 | `WarehouseSaveDTO` |
| `QueryDTO` | 查询条件 | `WarehouseQueryDTO` |
| `VO` | 返回给调用方 | `WarehouseVO` |

## 3. 编码规范

### 命名

| 类型 | 规则 |
|---|---|
| 类 / 接口 | 大驼峰 `WarehouseService` |
| 方法 / 变量 | 小驼峰 `queryAvailableInventory` |
| 常量 / 枚举值 | 全大写下划线 `PUTAWAY_DONE` |
| 数据库表 / 字段 | 小写下划线 `inbound_order`、`create_time` |
| URL | 小写中划线复数 `/inbound-orders` |

方法名用业务语义（`allocateStock`），不用技术语义（`update2`、`getList`）。

### Controller

```java
@Tag(name = "基础数据 - 仓库")
@RestController
@RequestMapping("/api/v1/basedata/warehouses")
@RequiredArgsConstructor
public class WarehouseController {

    private final WarehouseService warehouseService;

    @Operation(summary = "分页查询仓库")
    @GetMapping
    public Result<PageResult<WarehouseVO>> page(@Validated WarehouseQueryDTO query) {
        return Result.success(warehouseService.page(query));
    }
}
```

只用「接收 → 委托 → 返回」，不写 try-catch（交给全局异常处理）。
用构造器注入（`@RequiredArgsConstructor` + `final`），不用 `@Autowired` 字段注入。

### Service

- 写操作才加 `@Transactional(rollbackFor = Exception.class)`
- 业务校验失败抛 `BizException`，不要返回布尔值让上层判断
- 事务方法内**不要**做远程调用、发消息
- 注意：同类内部方法调用不走代理，事务注解会失效

### SQL

- 简单单表用 MyBatis-Plus 方法，复杂查询写 XML
- 显式列出字段，禁止 `SELECT *`
- 动态值一律 `#{}`，禁止 `${}`；排序字段必须白名单校验
- 列表查询禁止 N+1，必须批量查

### 日志

- 用占位符 `log.info("收货开始, orderId={}", orderId)`，不要字符串拼接
- 关键节点打点：操作开始、结果、状态变化
- 业务异常 `warn` 不带堆栈，系统异常 `error` 带堆栈
- 用 MDC 透传 traceId
- 禁止 `System.out.println`、禁止循环内大量打日志

### 时间与数量

- 时间统一 `LocalDateTime`，禁止 `java.util.Date`
- 数量统一整数，禁止浮点

## 4. 接口规范

### 4.1 URL

```
/api/v1/{module}/{resource}                    查询 / 创建
/api/v1/{module}/{resource}/{id}               详情 / 更新 / 删除
/api/v1/{module}/{resource}/{id}/{action}      动作（状态流转）
```

动作型接口的例子：

```
POST /api/v1/inbound/inbound-orders/{id}/receive     收货
POST /api/v1/outbound/outbound-orders/{id}/allocate  分配库存
POST /api/v1/task/stock-tasks/{id}/assign            领取任务
```

用 `/id/action` 而不是硬套 CRUD，是因为「分配库存」改的到底是哪个资源，用 CRUD 说不清。

### 4.2 统一响应

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "traceId": "3f8a1c2e9b7d4a10",
  "timestamp": 1757558400000
}
```

分页时 `data` 为：

```json
{ "list": [], "total": 128, "pageNum": 1, "pageSize": 20, "pages": 7 }
```

分页参数 `pageNum` / `pageSize`，`pageSize` 上限 100（防止 `pageSize=999999` 拖垮数据库）。

### 4.3 错误码

分段：`0` 成功，`1xxxx` 通用，`2xxxx` 认证，`3xxxx` 基础数据，`4xxxx` 入库，`5xxxx` 库存，`6xxxx` 出库，`7xxxx` 任务。错误码必须用枚举定义，禁止硬编码数字。

| code | 说明 |
|---|---|
| 10001 | 系统繁忙 |
| 10002 | 参数校验失败 |
| 10004 | 资源不存在 |
| 10006 | 数据已被修改，请重试（乐观锁冲突） |
| 10007 | 重复请求，请勿重复提交 |
| 10008 | 当前状态不允许该操作 |
| 20001 / 20002 | 未登录 / 登录已过期 |
| 20003 | 无权限 |
| 30002 | 仓库编码已存在 |
| 30009 | 库位容量不足 |
| 30012 | 存在关联数据，无法删除 |
| 40002 | 入库单状态不允许该操作 |
| 40004 | 实收数量超过预计数量 |
| 50001 | 库存不足 |
| 50005 | 库存被并发修改，请重试 |
| 60003 | 可用库存不足，分配失败 |
| 60005 | 存在未完成的拣货任务 |
| 70003 | 任务已被领取 |

HTTP 状态码只管协议层（401 未登录、403 无权限、500 系统异常），业务错误看响应体里的 `code`。

### 4.4 请求头

| 头 | 说明 |
|---|---|
| `Authorization` | `Bearer {token}` |
| `X-Trace-Id` | 链路 ID，不传则服务端生成 |
| `X-Idempotent-Key` | 幂等键，写接口建议必传 |

### 4.5 幂等设计

写接口必须防重复。优先用业务唯一键，而不是只靠调用方传的幂等键。

```
1. 拼幂等 key（bizType + 业务键），尝试 INSERT idempotent_record
   ├─ 插入成功 → 首次，执行业务；成功后把状态改成 1
   └─ 唯一键冲突 → 重复请求
         ├─ 状态 1 → 直接返回上次结果
         ├─ 状态 0 → 返回 10007「处理中」
         └─ 状态 2 → 允许重试
2. 兜底：数据库唯一约束（单号、流水号）
```

多层防护：应用层去重 + 数据库唯一约束 + 状态机校验。

### 4.6 参数校验

分两层：格式校验（非空、长度、范围）放 DTO 注解在 Controller 层；业务校验（存在性、状态合法性）放 Service。

## 5. 索引与性能

- 等值字段在前，范围字段在后（最左前缀）
- 高频组合查询建联合索引
- 所有 `xxx_id` 关联字段建索引
- 用 `EXPLAIN` 验证，禁止大表全表扫描
- 深分页用游标：`WHERE id > #{lastId} ORDER BY id LIMIT 20`，而不是 `LIMIT 200000, 20`

**高频追问预案**

| 追问 | 要点 |
|---|---|
| 为什么不用分布式锁？ | 单库能用 DB 锁解决；分布式锁多一个故障点，先说清收益 |
| 库存为什么不用 Redis 做主存储？ | 持久化、事务、对账、可靠性；Redis 适合做缓存和预扣减 |
| 消息重复消费怎么办？ | 消费端幂等：业务唯一键 + 唯一索引 |
| 缓存与数据库不一致怎么办？ | 延迟双删，或订阅 binlog，说明取舍 |
| 出库为什么不直接扣库存？ | 三阶段模型，拣货可能失败，把不可逆操作推到最后 |

## 8. 开发习惯

- 一次只打通一个接口，从 Controller → Service → Mapper 走通，别攒着
- 每写完一个接口立刻在 Knife4j 里调一次
- 发现设计不合理 → **先改文档再改代码**
- 每周结束写 200 字总结：学了什么、踩了什么坑、怎么解决的
