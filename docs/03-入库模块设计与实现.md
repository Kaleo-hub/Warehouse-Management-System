# 03 · 入库模块设计与实现

本文记录入库链路（建单 → 收货 → 生成上架任务 → 执行上架 → 库存增加）的**关键设计决策**。
每条都按「问题 → 方案 → 为什么 → 面试怎么讲」组织，可以直接拿来准备面试。

对应代码：

```
wms-server/src/main/java/com/myproject/wmsserver/
├── inbound/      入库单、收货
├── inventory/    库存内核、库存与流水查询
├── task/         上架任务状态机
└── common/sequence/  单号发号器
```

---

## 1. 链路全景

### 1.1 状态机

```
入库单
  CREATED ──收货──> RECEIVING ──收完──> RECEIVED ──全部上架完──> PUTAWAY_DONE
     └──取消──> CANCELLED

上架任务
  CREATED ──领取──> ASSIGNED ──开始──> PROCESSING ──完成──> DONE
```

**单据状态 `PUTAWAY_DONE` 不是人工点的**，是最后一个上架任务完成时由系统自动推进的。

### 1.2 数据流（一次完整的入库）

```
① 建单     POST /inbound-orders
           ├─ 发号器取 orderNo
           ├─ 从 product 复制 skuCode/skuName 做快照
           └─ 状态 CREATED                          → 不碰库存

② 收货     POST /inbound-orders/{id}/receive
           ├─ 锁单据行（FOR UPDATE）
           ├─ 校验：累计实收 ≤ 预计
           ├─ 累加明细 received_qty
           └─ 状态 → RECEIVING 或 RECEIVED          → 不碰库存 ★

③ 派活     POST /inbound-orders/{id}/putaway-tasks
           ├─ 按「实收 - 已上架」生成任务
           ├─ 推荐目标库位
           └─ 幂等：已有在途任务不重复生成            → 不碰库存

④ 作业     POST /stock-tasks/{id}/assign → /start

⑤ 上架     POST /stock-tasks/{id}/complete
           ├─ ① CAS 占状态 PROCESSING → DONE
           ├─ ② InventoryService.applyChange 加库存 ★★★ 唯一写库存的地方
           ├─ ③ 增加库位已用容量（BR-006）
           └─ ④ 回写明细 putaway_qty，全部完成则单据 → PUTAWAY_DONE
```

**注意 ② 和 ⑤ 的区别**：收货只是记账（货还在暂存区），上架完成才是货真正进入库存。

### 1.3 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/inbound/inbound-orders` | 入库单分页 |
| POST | `/api/v1/inbound/inbound-orders` | 创建 |
| GET | `/api/v1/inbound/inbound-orders/{id}` | 详情（含明细） |
| POST | `/api/v1/inbound/inbound-orders/{id}/receive` | 收货登记 |
| POST | `/api/v1/inbound/inbound-orders/{id}/cancel` | 取消 |
| POST | `/api/v1/inbound/inbound-orders/{id}/putaway-tasks` | 生成上架任务 |
| GET | `/api/v1/inventory/inventories` | 库存分页 |
| GET | `/api/v1/inventory/transactions` | 流水分页 |
| GET | `/api/v1/task/stock-tasks` | 任务分页 |
| POST | `/api/v1/task/stock-tasks/{id}/assign` | 领取 |
| POST | `/api/v1/task/stock-tasks/{id}/start` | 开始 |
| POST | `/api/v1/task/stock-tasks/{id}/complete` | 完成上架 |

## 2. 关键设计

### 2.1 库存唯一写入口：`InventoryService.applyChange`

**问题**：上架要加库存、出库要锁库存、移库要减一边加一边、盘点要改数量。
如果每个业务各写一段 `UPDATE inventory SET qty = qty + 1`，会出现：

- 有人忘了写流水 → BR-008 破了，账对不上
- 有人忘了判负数 → 库存变成 -5
- 有人并发下算错 → 两个人同时上架，加了两次

**方案**：`InventoryService` 上**只有一个写方法** `applyChange`，任何业务都不允许直接 `UPDATE inventory`。

```java
@Transactional(rollbackFor = Exception.class)
public void applyChange(InventoryChangeCommand command) {
    // ① 确保库存行存在   INSERT ... ON DUPLICATE KEY UPDATE   （BR-003）
    // ② 锁行拿当前值     SELECT ... FOR UPDATE
    // ③ 先算后校验       qty<0 / locked+frozen>qty 都拒绝
    // ④ 更新库存         UPDATE ... WHERE version = ?          （CAS 兜底）
    // ⑤ 写流水           INSERT inventory_transaction           （BR-008）
}
```

**五步全在同一个事务里**，任何一步抛异常整笔回滚，不会出现「改了库存没流水」。

**为什么第 ① 步不能省**：第 ② 步要 `FOR UPDATE` 锁行，而**不存在的行锁不住**。
第一次上架时这个「库位+SKU+批次」没有记录，两个并发请求会同时插入两条，BR-003 就破了。
`INSERT ... ON DUPLICATE KEY UPDATE id = id` 靠唯一键 `uk_loc_sku_batch` 保证幂等，并且会锁住唯一索引。

**面试怎么讲**：

> 「我把库存变动收敛成一个方法，所有业务必须走它，因为它要同时守住四条规则：
> 数量不能为负、可用不能为负、同库位 SKU 批次只有一条、每次变动必须写流水。
> 收口成一个方法之后，规则只需要在一处保证，不会因为某个业务忘了而破。
> 以后要换成 Redis 预扣减，也只改这一个地方。」

### 2.2 收货不写库存：把不可逆操作推到最后

**问题**：如果收货就增加库存，会怎样？

收货后货**还堆在收货暂存区**，可能：

- 清点发现破损，要退货
- 供应商送错货，要拒收
- 数量对不上，要重新核对

如果这时库存已经加了，就得写一大堆补偿逻辑把它减回去。

**方案**：收货只改单据和明细的 `received_qty`，**一行库存代码都不碰**。库存要等上架完成才增加。

```
收货：CREATED → RECEIVING → RECEIVED     （只记账）
上架：任务完成时 applyChange(+qty)        （才动库存）
```

**面试怎么讲**：

> 「收货不增加库存，上架完成才增加。因为收货之后货还在暂存区，
> 可能破损、可能拒收，这时候库存已经加了就得写补偿。
> 把不可逆的操作尽量往后推，前面就都是可回滚的。
> 这和出库那边『拣货不改库存、发货才扣账』是同一个思路。」

---

### 2.3 完成上架：先 CAS 占状态，再写库存

**问题**：两个请求同时完成同一个任务会发生什么？

如果先写库存再改状态：

```
A: 读到 status = PROCESSING
B: 读到 status = PROCESSING        ← 两个人都通过了检查
A: 库存 +100
B: 库存 +100                         ← 加了两次！
```

**方案**：**先 CAS 占状态，再写库存**。

```java
// ① 先占坑：只有把 PROCESSING 改成 DONE 成功的那个请求，才有资格继续
int affected = taskMapper.complete(taskId, actualQty, dto.getRemark());
if (affected == 0) throw new BizException(TASK_STATUS_NOT_ALLOWED);

// ② 才有资格写库存
inventoryService.applyChange(...);
```

```sql
UPDATE stock_task SET status = 'DONE', actual_qty = ?
 WHERE id = ? AND status = 'PROCESSING'   -- ← CAS 条件
```

第二个请求 `affected = 0`，直接抛 `70005`，**根本走不到写库存那一步**，而且失败得很快（不用等库存行锁）。

**为什么不怕中途失败**：整个方法有 `@Transactional`，第 ② 步失败会把第 ① 步的 CAS 一起回滚，**要么全做要么全不做**。

**实测**（`PutawayConcurrencyTest`）：10 个线程同时完成同一个任务 → **1 个成功、9 个被拒，库存只加了一次**。

**面试怎么讲**：

> 「完成上架我用 CAS 先占状态再写库存。先写库存的话，两个并发请求会都读到 PROCESSING、
> 都通过检查，然后各加一次库存。先 CAS 的话第二个请求在第 0 步就失败了，
> 而且失败得很快，不用去抢库存行锁。事务保证了后面失败会连 CAS 一起回滚。」

### 2.4 并发控制：行锁为主，`version` 为保险

**方案**：`applyChange` 里同时用了两种：

```sql
SELECT ... FROM inventory WHERE ... FOR UPDATE     -- 悲观锁（主）
UPDATE inventory SET ... , version = version + 1
 WHERE id = ? AND version = ?                       -- 乐观锁（兜底）
```

**诚实地说**：在 `FOR UPDATE` 生效的前提下，**那个 version CAS 永远命中不了** ——
后来的事务会被行锁挡住，等拿到锁时读到的必然是最新 version，所以它当前是冗余的。

**那为什么还留着**：

1. **防锁失效**：如果有人把方法调到事务外、或者以后重构把 `FOR UPDATE` 删了，
   version 会**抛异常**而不是静默丢更新（丢失更新是最难查的一类 bug）
2. **为对比实验留载体**：表上有 version 列，做「乐观锁 vs 悲观锁」压测时不用改表结构

**两种锁怎么选**：

| | 悲观锁 `FOR UPDATE` | 乐观锁 `version` |
|---|---|---|
| 冲突时的表现 | 后来的**排队等** | **立即失败**，自己重试 |
| 适合 | 冲突率**高**（热点行） | 冲突率**低** |
| 不适合 | 读多写少 | 热点行（重试次数爆炸，白烧 CPU） |
| 实现 | 简单 | 要写重试循环 + 控制重试上限 |

库存扣减是**典型热点行**（同一个爆款 SKU 同时被几十个订单扣），所以选悲观锁。
真正的高并发方案是 Redis 预扣减 + 异步落库。

**面试怎么讲**（这里千万别硬说"双保险"）：

> 「主线用悲观锁，因为库存扣减是热点行，冲突率高，乐观锁重试成本不划算。
> 表上保留了 version 列，但坦白说在 FOR UPDATE 生效的前提下它是冗余的 ——
> 我保留它一是防止锁失效时静默丢更新，二是要做两种方案的压测对比。
> 如果以后有低冲突的场景（比如后台改基础数据），会换成纯乐观锁 + 重试。」

### 2.5 加锁还是 CAS：两个场景的对比

同样是状态流转，代码里用了两种不同的写法：

| 场景 | 做法 | 为什么 |
|---|---|---|
| **收货** | `SELECT ... FOR UPDATE` 锁单据行 | 要**读明细 → 算总量 → 写回**，中间不能被插队 |
| **取消单据** | 一条带 `status` 条件的 UPDATE | **不需要读原始数据**，一条 SQL 本身就是原子的 |

取消的实现：

```sql
UPDATE inbound_order SET status = 'CANCELLED'
 WHERE id = ? AND status = 'CREATED' AND deleted = 0
-- 影响行数 0 → 状态不对 → 抛 40002
```

**这里的 `status` 本身就充当了版本号** —— 它同时承担「校验当前状态合法」和「防止并发重复流转」两个职责，
所以不需要额外的 version 列。

**判断标准**：**要不要先读后写**。要读，就得锁；不用读，一条 CAS 就够。

### 2.6 单号发号器：为什么不用 `MAX(order_no) + 1`

**问题**：

```sql
SELECT MAX(order_no) FROM inbound_order WHERE order_no LIKE 'IN20260918%';
-- 两个请求同时查到 ...0005，都生成 ...0006
-- 最后只有一个能插入成功（唯一索引挡住），另一个报错
```

并发一高，用户就会看到"创建偶尔失败"。

**方案**：`sys_sequence` 表 + `INSERT ... ON DUPLICATE KEY UPDATE`。

```sql
INSERT INTO sys_sequence (biz_type, biz_date, current_value)
VALUES ('INBOUND_ORDER', '20260918', 1)
ON DUPLICATE KEY UPDATE current_value = current_value + 1;
```

- 主键是 `(biz_type, biz_date)`，**每个「业务类型 × 每天」一行**，互不干扰
- InnoDB 会对这一行加排他锁，**并发请求自动排队**，天然不会重号
- **不需要预置任何数据** —— 第一次用到哪行就长出哪行，一年约 1000 行

同一个发号器被入库单（`IN`）和上架任务（`TASK`）复用，出库单以后也能直接用。

### 2.7 序号有空洞，是刻意的

发号走**独立事务**：

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public String nextNo(String bizType, String prefix) { ... }
```

序号一旦发出去就**不回收**。所以业务失败回滚后，那个号就废了。

**如果让发号跟着业务事务回滚会怎样**：

```
A: 拿到 0006 → 业务失败 → 回滚 → 序号退回 5
B:              拿到 0006 → 插入成功
```

看起来没事，但如果**已经有异步操作或别的系统看到了 `0006`** 呢？
单号一旦出现在世界上就不该被收回。

**代价**：单号有空洞（0006 作废、下一单 0007）。这完全可接受 —— 所有正经系统的单号都有空洞。

**实测数据**：开发过程中发号器发到 87，但库里只有 5 张单据，中间的都是测试用例消耗的。

### 2.8 SKU 快照

**问题**：入库明细如果只存 `sku_id`，靠 JOIN 查商品名，会怎样？

商品改名后，**三个月前的历史单据会显示现在的名字**。对账时会对不上（"当时明明是叫这个"）。

**方案**：建单时把 `sku_code` / `sku_name` **复制一份存进明细表**。

```java
// 存快照，不靠 join
item.setSkuCode(sku.getSkuCode());
item.setSkuName(sku.getName());
```

**代价**：商品改名后数据冗余、不一致。但**这是故意的** —— 单据要反映"当时的事实"。

> 同理：库存表也会冗余，但从 `product` JOIN 是没问题的 —— 因为库存是**当前状态**，
> 展示当前商品名才合理。而单据是**历史事实**，必须用快照。
> 这是「快照 vs 实时关联」的取舍判断点。

### 2.9 流水记 `qty_before` / `qty_after`，支持对账

**问题**：怎么验证「库存余额」和「流水」是一致的？

如果流水只记变动量，对账就得**从头重算全部历史** —— 数据量一大就跑不动。

**方案**：每条流水都记下变动前后：

```java
tx.setQtyBefore(qtyBefore);   // 变动前
tx.setQtyAfter(qtyAfter);     // 变动后
```

对账只要扫一遍流水，看**上一条的 `qty_after` 是不是等于下一条的 `qty_before`**，不连续就有问题。
不用重算，一次扫描就够。

另外流水表**没有 `deleted` 字段**，全局逻辑删除对它不生效 —— 这正是想要的，流水永远留着。

### 2.10 幂等：生成上架任务

**问题**：用户手抖点两次「生成上架任务」，会不会派两份活？

**方案**：生成前先查这张单**已有的在途任务**（`status != DONE/CANCELLED`），它们覆盖的明细跳过。

```java
Set<Long> busyItemIds = existing.stream()
        .map(StockTask::getSourceItemId)
        .collect(Collectors.toSet());
...
if (busyItemIds.contains(item.getId())) continue;   // 已经派过活了
```

一条都没生成 → 抛 `10007 重复请求，请勿重复提交`。

**注意这里用的是「业务唯一键」而不是幂等键** —— 判断依据是"这张明细有没有在途任务"，
这个判断天然幂等，不依赖调用方传什么 `X-Idempotent-Key`。

### 2.11 模块依赖方向：避免循环依赖

```
task → inbound / inventory / basedata      （单向）
inbound → basedata / common                （不反向依赖 task）
```

**为什么重要**：如果 `InboundOrderService` 调 `StockTaskService`，
而 `StockTaskService` 又要调 `InboundOrderService` 回写状态，两个 Service 互相注入 →
**Spring 启动直接报循环依赖**（除非加 `@Lazy` 或 `allow-circular-references`，那是掩盖问题）。

**怎么做到单向**：仓库的依赖方向由「谁拥有数据」决定：

- 任务由 task 创建 → `StockTaskService.generatePutawayTasks()` 读入库单（调 InboundOrderService）
- 单据状态由 inbound 自己维护 → 上架完成时，task 调 `InboundOrderService.onPutawayCompleted()` **通知**它

**"生成上架任务"这个接口挂在入库单下面**（`POST /inbound-orders/{id}/putaway-tasks`），
但实现由 task 模块负责，所以是 `InboundOrderController` 直接调 `StockTaskService`，控制器可以依赖任意模块。

**跨模块只调 Service，不注入别人的 Mapper**：这样对方的内部实现（表结构、SQL）
变了不会影响你。唯一的例外是**只读的跨模块 JOIN 查询**
（比如库位推荐要同时读 location 和 inventory），那是「读投影」不是「写别人的表」，
放在自己的 Mapper 里是可以接受的。

### 2.12 容量校验原子化（BR-006）

**问题**：上架后库位不能超容。如果写成「先查容量够不够，再更新」：

```
A: 查到剩 50 可用
B: 查到剩 50 可用
A: 放 40 进去 → 剩 10
B: 放 40 进去 → 超了 30 ✗
```

**方案**：把「判断」和「更新」合成一条 SQL：

```sql
UPDATE location
SET used_capacity = used_capacity + #{qty}
WHERE id = #{id}
  AND deleted = 0
  AND (capacity = 0 OR used_capacity + #{qty} <= capacity)
```

> `capacity = 0` 表示不限容量（收货暂存位）。
> 影响行数 0 → 抛 `30009 库位容量不足`。

这条 SQL 本身就是原子的，并发下不会两个都通过检查然后一起超容。

**和 2.5 是同一个思路**：能一条 SQL 解决的事，不要「先查再改」。

### 2.13 写入口与查询分离

`inventory` 包下有两个 Service：

| Service | 方法 | 说明 |
|---|---|---|
| `InventoryService` | `applyChange` | **只有这一个方法**，唯一写入口 |
| `InventoryQueryService` | `pageInventory` / `pageTransaction` | 只读查询 |

**为什么分开**：如果查询方法也塞进 `InventoryService`，那个类就会有十个方法，
以后别人看到「这里本来就有很多库存相关方法」，很容易顺手加一个 `updateXxx` ——
**安全边界就模糊了**。

分开之后 `InventoryService` 永远只有一行方法签名，一眼就能确认「改库存只有这一条路」。

**面试怎么讲**：

> 「我把库存的读写拆成两个 Service。写的那边只有一个方法，因为它是安全边界 ——
> 任何人想改库存都只能走它。查询是另一回事，混在一起时间长了边界就守不住了。」

### 2.14 序列化和反序列化必须对称

**踩过的坑**：`JacksonConfig` 只注册了 `LocalDateTimeSerializer`（输出 `yyyy-MM-dd HH:mm:ss`），
没注册反序列化器。结果 **API 输出的是空格格式，接收时 Jackson 却按 ISO-8601（带 `T`）解析**。

前端的日期选择器恰好按 API 输出的格式回传，于是**建单接口一调就报 `10003 请求体格式错误`**。

**修复**：新增 `FlexibleLocalDateTimeDeserializer`，同时兼容三种写法：

```
2026-09-20 09:00:00        接口输出格式（前端在用）
2026-09-20T09:00:00        ISO-8601，兼容 Postman / Swagger
2026-09-20T09:00:00.123    带毫秒，自动截断
```

**教训**：**API 输出什么格式，就必须能接收什么格式。** 序列化器和反序列化器要成对注册。

> 这个 bug 自己测接口时很难发现 —— 用 Knife4j / Postman 手写 JSON 时，
> 你多半会顺手写成 ISO 格式，反而是对的。只有前端真正接上才会暴露。

## 3. 错误码

### 两条必须跑的并发用例

```java
// PutawayConcurrencyTest
10 个线程同时 complete 同一个任务 → 1 成功，库存只加一次
10 个作业员同时 assign 同一个任务 → 1 成功，其余 70003
```

这两条正好对应 docs/02 里的「面试亮点 #4 状态机 + CAS」。

> **写并发测试要注意**：不能加 `@Transactional`。
> 测试事务是**一个**事务，而并发线程走各自的连接、各自的事务，
> 既看不到测试事务未提交的数据，测试回滚也清不掉线程写的数据。
> 改成 `@AfterEach` 里物理清理。

## 5. 踩过的坑（真实记录）

| # | 现象 | 根因 | 教训 |
|---|---|---|---|
| 1 | 建单接口报 `10003 请求体格式错误` | Jackson 只注册了序列化器，没注册反序列化器 | **API 输出什么格式就要能接收什么格式** |
| 2 | 会话过期后永远跳不回登录页 | `clearAuthStorage()` 只清 localStorage，Pinia 内存里的 token 还在，路由守卫把 `/login` 弹回首页 | 清登录态要**同时清内存和持久化**；必须测 token 失效这条负向路径 |
| 3 | Mock 数据改了但页面不刷新 | mock adapter 返回对象引用，Vue 检测不到变化 | 接口要返回**深拷贝**，模拟真实 HTTP 的 JSON 往返 |
| 4 | 点「领取」提示"无法连接后端" | 局部变量 `taskAction` 把同名处理函数遮蔽了 | 这类错误**只有端到端测试能发现** |
| 5 | 表格固定列被长文本"透"上来 | `--el-table-tr-bg-color: transparent`，固定列没有背景色遮不住内容 | sticky 固定列**必须有不透明背景** |
| 6 | 清理测试数据后同一条库存再也插不进去 | 逻辑删除把 `deleted` 置 1，但唯一索引 `uk_loc_sku_batch` **不含 deleted** | 唯一索引 + 逻辑删除**要一起设计** |
| 7 | `SELECT ... FOR UPDATE` 锁不住 | 行不存在，锁不存在的行是无效的 | 先 `INSERT ... ON DUPLICATE KEY UPDATE` 占位，再锁 |

**第 6 条值得单独说**：库存表用了逻辑删除 + `uk_loc_sku_batch` 唯一键。
如果某个库位的库存被软删了（`deleted = 1`），
那么**同一个「库位+SKU+批次」永远插不回来了** —— 唯一键冲突。

要么唯一键里带上 `deleted`（但同一行删两次还是冲突），
要么库存表**根本不该逻辑删除**（库存为 0 时物理删除，或者干脆不删）。
