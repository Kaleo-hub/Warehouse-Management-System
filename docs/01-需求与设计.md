## 3. 业务规则

代码注释和测试用例直接引用编号。

| 编号 | 规则 |
|---|---|
| BR-001 | `qty` / `locked_qty` / `frozen_qty` 任何时刻都不得为负 |
| BR-002 | 可用数量 = 在库 − 锁定 − 冻结，分配只能用可用部分 |
| BR-003 | 同一「库位 + SKU + 批次」只允许一条库存记录 |
| BR-004 | 出库分配遵循 FIFO：优先入库早、生产日期早的批次 |
| BR-005 | 冻结的库存不可分配、不可移库 |
| BR-006 | 上架后库位已用容量不得超过容量上限 |
| BR-007 | 单据与任务的状态只能沿状态机定义的边流转，禁止跳跃与回退 |
| BR-008 | 每次库存变动都必须写一条库存流水，流水只增不改不删 |
| BR-009 | 库存余额必须能由流水重算，不一致时以流水为准并告警 |
| BR-010 | 出库单分配后超时未拣货，需自动释放锁定库存 |
| BR-011 | 已发货的单据不可撤销，只能开反向单 |
| BR-012 | 所有写接口需幂等，重复提交不得产生重复效果 |
| BR-013 | 单据编号全局唯一：前缀 + yyyyMMdd + 6 位序号，如 `IN20260911000001` |
| BR-014 | 逻辑删除的数据不参与业务查询 |
| BR-015 | 库存变动必须记录操作人与时间 |
| BR-016 | 存在已完成上架任务的入库单不可取消 |
| BR-017 | 数量统一用整数，单位由商品的最小计量单位决定 |

## 4. 领域模型

### 4.1 层级关系

```
仓库 Warehouse
 └── 库区 Zone（存储区 / 拣货区 / 收货区 / 发货区）
```

### 4.3 库存表为什么这么设计

```sql
qty            -- 在库实物数量
locked_qty     -- 已被订单占用、未出库
frozen_qty     -- 盘点 / 质检中，不能动
available_qty  -- 生成列 = qty - locked_qty - frozen_qty
version        -- 乐观锁
batch_no       -- 无批次用空串（用 NULL 会让唯一约束失效）
```

**为什么不用一个状态字段表达锁定？** 部分锁定是常态：一批 10 件，订单锁 3 件，剩 7 件还能被别的单用。单状态字段表达不了。

**为什么 `available_qty` 用生成列？** 不让应用层自己算，避免算错；`STORED` 生成列还能建索引。

**为什么流水带 `qty_before` / `qty_after`？** 对账时直接看相邻流水是否连续，不用重算全部历史。

### 4.4 其他约定

- 时间统一 `datetime(3)`，Java 用 `LocalDateTime`
- 状态字段存枚举名（`CREATED` 这类），Java 侧用枚举强类型
- 不用数据库外键，由应用层保证（并发下外键有额外锁开销，且分库后失效）
- 主数据逻辑删除，流水不删，幂等记录物理删除

## 5. 核心流程

### 5.1 入库

```
创建入库单 → 收货登记 → 生成上架任务 → 执行上架 → 库存增加
（CREATED）  （RECEIVING）  （RECEIVED）      （任务）   （PUTAWAY_DONE）
```

注意：**收货不增加库存，上架完成才增加。**

### 5.2 出库

```
创建出库单 → 分配库存 → 拣货 → 复核 → 发货 → 库存减少
（CREATED）  （ALLOCATED）  （PICKING） （PICKED） （SHIPPED）
```

三阶段库存模型：

| 阶段 | qty | locked_qty | 说明 |
|---|---|---|---|
| 分配 | 不变 | +n | 占用可用库存，货还没动 |
| 拣货 | 不变 | 不变 | 实物已取出，账面未动 |
| 发货 | −n | −n | 账实核销 |

**为什么拣货不改库存？** 拣货可能失败，若此时扣账就要写补偿逻辑。把不可逆操作推到最后更稳。

### 5.3 出库分配算法（FIFO）

```
FOR EACH 明细:
  need = 需求数量
  candidates = SELECT * FROM inventory
                WHERE warehouse_id=? AND sku_id=?
                  AND qty - locked_qty - frozen_qty > 0
                ORDER BY inbound_time ASC, production_date ASC

  FOR EACH 候选:
     take = MIN(need, 可用数量)
     UPDATE inventory SET locked_qty = locked_qty + take, version = version + 1
      WHERE id=? AND version=? AND qty - locked_qty - frozen_qty >= take
     -- 影响行数为 0 说明被并发改过或库存不足 → 重试或失败

     写 outbound_allocate + 写库存流水（ALLOCATE_LOCK）
     need -= take

  IF need > 0 THEN 整单回滚，返回「库存不足」
```

整单原子：任一明细分配失败就全部回滚。

## 6. 状态机

三张状态机，箭头表示允许的流转。**只能沿箭头走，禁止跳跃和回退。**

### 6.1 入库单

```
CREATED ──收货──> RECEIVING ──收完──> RECEIVED ──上架完成──> PUTAWAY_DONE ──> CLOSED
   └──取消──> CANCELLED
```

### 6.2 出库单

```
CREATED ──分配──> ALLOCATED ──开始拣货──> PICKING ──拣完──> PICKED ──发货──> SHIPPED ──> CLOSED
   │                  │
   └──取消──> CANCELLED └──释放/超时──> CREATED
```

**`PICKING` 不能回退**：实物已经拣出去了，强行释放会造成账实不符，只能走人工处理。

### 6.3 作业任务

```
CREATED ──领取──> ASSIGNED ──开始──> PROCESSING ──> DONE
   │                  │                   └──异常──> EXCEPTION
   ├──取消──> CANCELLED
   └──超时──> TIMEOUT ──重新入池──> CREATED（只重试一次）
```

### 6.4 状态流转必须并发安全

不要「先查再改」，要用 CAS：

```sql
UPDATE inbound_order
   SET status = 'RECEIVING', version = version + 1
 WHERE id = ? AND status = 'CREATED';
-- 影响行数为 0 → 状态已被别人改过 → 抛业务异常
```

三层防护：状态机校验 + CAS 更新 + 数据库约束。

## 7. 库存变动规则

| 操作 | qty | locked_qty | frozen_qty | 流水类型 |
|---|---|---|---|---|
| 上架入库 | +n | 0 | 0 | `PUTAWAY_IN` |
| 出库分配 | 0 | +n | 0 | `ALLOCATE_LOCK` |
| 释放分配 | 0 | −n | 0 | `ALLOCATE_RELEASE` |
| 出库发货 | −n | −n | 0 | `OUTBOUND_OUT` |
| 冻结 | 0 | 0 | +n | `FREEZE` |
| 解冻 | 0 | 0 | −n | `UNFREEZE` |
| 移库转出 / 转入 | −n / +n | 0 | 0 | `TRANSFER_OUT` / `TRANSFER_IN` |
| 盘盈 / 盘亏 | +n / −n | 0 | 0 | `STOCKTAKING_GAIN` / `STOCKTAKING_LOSS` |

任何操作后都必须成立：`qty >= 0`、`locked_qty >= 0`、`frozen_qty >= 0`、`locked_qty + frozen_qty <= qty`。

## 8. 异常与补偿

| 场景 | 处理 |
|---|---|
| 分配后超时未拣货 | 定时扫描（第 8 周改延迟队列）→ 释放锁定、作废任务、单据回 `CREATED` |
| 拣货数量不足 | 任务置 `EXCEPTION`，单据停在 `PICKING`，等人工重新分配 |
| 任务超时未处理 | 置 `TIMEOUT`，重试一次回任务池 |
| 余额与流水不一致 | 对账任务扫出来，以流水为准重算并告警 |
