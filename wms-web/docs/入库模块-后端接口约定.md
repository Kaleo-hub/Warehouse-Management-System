# 入库模块 · 后端接口约定

入库链路（入库单 / 收货 / 上架任务 / 库存 / 流水）的接口契约。
**后端已按本文档实现并端到端联调通过**，前端零改动接通。

> 模块的设计决策与踩坑记录见后端仓库的 `docs/03-入库模块设计与实现.md`。

涉及三块：`inbound`（单据 + 收货）、`inventory`（库存 + 流水）、`task`（上架任务）。

---

## 0. 建议的实现顺序

先把 `inventory` 的写入内核做掉，再做单据，最后做任务：

```
① InventoryService.applyChange(...)   ← 库存唯一写入口（先写它）
② 入库单 CRUD + 收货                    ← 不碰库存
③ 生成上架任务 + 完成上架               ← 调 ① 加库存
④ 库存查询 / 流水查询                   ← 只读，最简单
```

原因：收货不写库存，上架才写。如果先铺单据，做完还是没有任何库存数据，查不了也测不了。
而 `applyChange` 一旦写对，后面出库、移库、盘点全部复用。

### 2.2 创建入库单

```
POST /api/v1/inbound/inbound-orders
```

```json
{
  "warehouseId": 1,
  "supplierName": "华东日化供应链有限公司",
  "expectArriveTime": "2026-09-16 10:00:00",
  "remark": "",
  "items": [
    { "skuId": 4, "expectQty": 80, "remark": "" }
  ]
}
```

- `items` 至少一条；`expectQty > 0`
- 服务端生成 `orderNo`（建议 `IN + yyyyMMdd + 6位序号`）、`totalExpectQty` 求和、状态置 `CREATED`
- **`skuCode` / `skuName` 要落库做快照**（商品改名后历史单据不能跟着变）
- 返回：`Result<Long>`，`data` = 新建单据 id（前端用它跳详情）

### 2.4 收货登记 ★

```
POST /api/v1/inbound/inbound-orders/{id}/receive
```

```json
{
  "items": [
    {
      "itemId": 104,
      "receivedQty": 80,
      "batchNo": "B20260918A",
      "productionDate": "2026-09-01",
      "expiryDate": "2028-08-31"
    }
  ]
}
```

**设计要点（前端已按此实现，请务必对齐）：**

1. **整单一次提交，不是一个明细一个请求**。前端点一次「提交收货」发一个请求，body 里带多行。
   好处：事务边界清晰，任一行不合法整单回滚，符合你文档里「整单原子」的思路。
2. 前端只会提交 `receivedQty > 0` 的行，但后端**仍要校验**：
   - `itemId` 必须属于该单据
   - `receivedQty > 0`
   - **`receivedQty + 明细已有的 received_qty <= expect_qty`**，否则返回 `40004 实收数量超过预计数量`
3. `batchNo` / `productionDate` / `expiryDate` 允许为空，可覆盖写入
4. 收货完成后重算 `total_received_qty`，并按规则推进状态：
   - 所有明细 `received_qty >= expect_qty` → **`RECEIVED`**
   - 否则 → **`RECEIVING`**
5. **这一步绝对不要碰 `inventory` 表**。这是整个设计的核心：收货不增加库存，上架完成才增加。
6. 返回：`Result<Void>`

> 并发提醒：同一单据不能同时被两个人收货。用 `UPDATE ... WHERE id=? AND status IN ('CREATED','RECEIVING')` 或行锁保证。

### 2.5 取消入库单

```
POST /api/v1/inbound/inbound-orders/{id}/cancel
```

- 只有 `CREATED` 允许取消（状态机 `CREATED ──取消──> CANCELLED`）
- 否则返回 `40002 入库单状态不允许该操作`
- 建议用 CAS：`UPDATE inbound_order SET status='CANCELLED', version... WHERE id=? AND status='CREATED'`，
  影响行数为 0 就抛 `40002`
- 返回：`Result<Void>`

### 2.6 生成上架任务

```
POST /api/v1/inbound/inbound-orders/{id}/putaway-tasks
```

- 只有 `RECEIVED` 允许
- 对每条「`received_qty - putaway_qty > 0`」的明细生成一条 `PUTAWAY` 任务
- **单据状态保持不变**（还是 `RECEIVED`）。真正的 `PUTAWAY_DONE` 是在所有任务完成后由任务侧回写的
- **幂等**：同一明细已存在未完成任务时不要重复生成（业务唯一键：
  `source_type + source_id + source_item_id + status != DONE/CANCELLED`），重复请求返回 `10007`
- 库位推荐（P1，可以先简单来）：
  1. 同仓库、`ENABLED`、`location_type = 'RACK'`
  2. 优先已有该 SKU 库存的库位
  3. 其次按 `used_capacity` 升序
  4. `from_location_id` 取同仓库的 `TEMP` 暂存位
- 返回：`Result<Integer>`，`data` = 本次生成的任务数（前端目前不展示，但方便你调试）

**三个动作的状态机与并发要求：**

| 动作 | 允许的前置状态 | 目标状态 | 失败错误码 |
|---|---|---|---|
| assign | `CREATED` | `ASSIGNED` | 被人抢走 → `70003 任务已被领取` |
| start | `ASSIGNED` | `PROCESSING` | `10008` |
| complete | `PROCESSING` | `DONE` | `10008` |

`assign` 必须用 CAS，**不能先查再改**：

```sql
UPDATE stock_task
   SET status = 'ASSIGNED', assignee_id = ?, assignee_name = ?
 WHERE id = ? AND status = 'CREATED';
-- 影响行数 0 → 已被别人领走 → 抛 70003
```

## 3. 库存写入内核（最重要的一节）

所有会改 `inventory` 的地方，都必须走同一个方法。**不要在任何 Service 里直接 `UPDATE inventory`。**

```java
/**
 * 库存唯一写入口：改库存 + 写流水，必须在同一个事务里。
 * 对应 BR-008「每次库存变动都必须写一条库存流水」。
 */
@Transactional(rollbackFor = Exception.class)
public void applyChange(InventoryChangeCommand cmd) { ... }
```

一次调用要做完四件事：

1. **upsert 库存行**（满足 BR-003：同「库位 + SKU + 批次」只有一条）
   - 利用唯一键 `uk_loc_sku_batch(location_id, sku_id, batch_no)`
   - 推荐 `INSERT ... ON DUPLICATE KEY UPDATE qty = qty + VALUES(qty)`
   - 或用 `SELECT ... FOR UPDATE` 加锁后判断，**必须考虑并发**
2. **校验不变量**（BR-001 / BR-002）：
   `qty >= 0`、`locked_qty >= 0`、`frozen_qty >= 0`、`locked_qty + frozen_qty <= qty`
   —— 不满足直接抛业务异常，不要靠数据库 CHECK 兜底后才报 500
3. **写一条 `inventory_transaction`**
   - `tx_no` 全局唯一
   - **`qty_before` / `qty_after` 必须是变更前后同一个库位 + SKU + 批次的数量**，对账靠它
   - `tx_type` 严格用 `docs/01` 第 7 节的取值
4. **返回变更结果**（可选：返回 `qtyAfter`，方便上层判断）

`applyChange` 需要接收的参数：

| 参数 | 说明 |
|---|---|
| warehouseId | |
| locationId | |
| skuId | |
| batchNo | 无批次传空串，**不要传 null**（唯一键会失效） |
| qtyChange | 可正可负 |
| lockedChange / frozenChange | 本期先传 0 |
| txType | `PUTAWAY_IN` 等 |
| sourceType / sourceId / sourceNo | 来源单据 |
| operatorId / operatorName | 从 `UserContext` 取 |
| remark | |

### 上架完成时的调用顺序

```java
// StockTaskService.complete(...)
@Transactional(rollbackFor = Exception.class)
public void complete(Long taskId, CompleteDTO dto) {
    // 1. CAS 抢状态：PROCESSING → DONE（先占坑，避免并发重复上架）
    // 2. inventoryService.applyChange(PUTAWAY_IN, +actualQty, 目标库位)
    // 3. 回写 inbound_order_item.putaway_qty
    // 4. 若该入库单所有明细 putaway_qty >= received_qty
    //    → CAS 更新 inbound_order.status = 'PUTAWAY_DONE'
    // 5. 更新库位 used_capacity（可选，P2）
}
```

**顺序很关键**：先 CAS 占状态，再写库存。否则并发下同一个任务被执行两次，库存会加两遍。

| 10008 | 当前状态不允许该操作 | 提示 |
| 40002 | 入库单状态不允许该操作 | 提示 |

| 70003 | 任务已被领取 | 提示，刷新列表 |

**全部用 HTTP 200 + `code` 返回**（沿用你现有的约定）。

## 6. 自测验收清单

按顺序做一遍，全绿才算做完：

- [ ] 创建入库单 → 列表能看到，状态 `CREATED`，`totalExpectQty` 等于明细之和
- [ ] 详情能看到明细，`skuCode/skuName` 是快照
- [ ] 收货 80 → 状态 `RECEIVED`，`totalReceivedQty = 80`，**此时 `inventory` 表没有任何变化**
- [ ] 部分收货 50 → 状态 `RECEIVING`；再收 30 → `RECEIVED`
- [ ] 实收超过预计 → 返回 `40004`
- [ ] 对 `RECEIVED` 单据调 cancel → 返回 `40002`
- [ ] 生成上架任务 → 任务表出现记录，**重复调用返回 `10007`**
- [ ] 领取任务 → `ASSIGNED`；并发领取只成功一次，另一次返回 `70003`
- [ ] 开始 → `PROCESSING`
- [ ] 完成上架 → 任务 `DONE`，**`inventory` 新增一条且 `qty` 正确**，**`inventory_transaction` 新增一条 `PUTAWAY_IN`**
- [ ] 同一任务再调一次 complete → 返回 `10008`，**库存不会加第二遍**
- [ ] 单据所有明细上架完 → 单据自动变成 `PUTAWAY_DONE`
- [ ] 库存页 `availableQty = qty - lockedQty - frozenQty`
- [ ] 流水页 `qtyBefore` / `qtyAfter` 能和库存对得上

### 并发必测的两个点

1. **任务被两个人同时领取** → 只有一个成功
2. **同一个任务被并发 complete** → 只加一次库存

这两条是面试官最爱问的，也正好对应你文档里「面试亮点 #4 状态机 + CAS」。
