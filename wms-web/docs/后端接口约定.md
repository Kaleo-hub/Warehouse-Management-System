# 后端接口约定

前后端之间的接口契约。前端 `src/api/` 按这份文档调用，后端按这份文档实现 —— **目前已全部实现并联调通过**。

> 改动接口前请先更新本文档，避免前后端对不上。

---

## 1. 统一响应体

沿用后端已有的 `Result<T>`：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "traceId": "6ffdf896855c4f4392f5bf67fdd1329b",
  "timestamp": 1789556454657
}
```

前端处理规则（`src/api/request.js`）：

| 情况 | 前端行为 |
|---|---|
| `code === 0` | 直接返回 `data`，业务代码拿不到 `code`，只拿数据 |
| `code !== 0` | 抛 `ApiError(message, code, traceId)`，由页面决定提示方式 |
| `code` 为 `20001` / `20002` | 清理本地登录态，弹提示并跳回 `/login?redirect=当前路径` |
| 响应体不是 Result 结构 | 原样返回（给以后的文件下载留口子） |

> 登录页会把失败的 `traceId` 显示出来，方便和后端日志对齐，所以 **业务异常也要带上 traceId**。

## 2. 分页响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "records": [],
    "total": 26,
    "page": 1,
    "size": 10
  }
}
```

前端兼容 `records` 和 `list` 两种字段名，**推荐统一用 `records`**（对齐 MyBatis-Plus 的 `IPage`）。
请求参数固定为 `page`（从 1 开始）和 `size`。

## 3. 请求头

| 头 | 说明 |
|---|---|
| `Authorization` | `Bearer {token}`，登录后所有请求自动携带 |
| `X-Trace-Id` | 前端每次请求都会生成并带上，后端 `TraceIdFilter` 应优先使用它 |

## 4. 错误码映射（前端已处理的）

| code | HTTP | 前端表现 |
|---|---|---|
| 20001 | 401 | 清登录态 → 跳登录页 |
| 20002 | 401 | 同上，提示「登录已过期」 |
| 20003 | 403 | 提示「无权限访问该资源」 |
| 10004 | 404 | 提示「请求的接口不存在」 |
| 10001 | 500 | 提示「服务暂时不可用」 |
| 其它 | 200 | 直接用 `message` 提示用户 |

**约定：业务异常统一 HTTP 200 + 响应体里的 `code` 表达语义**，只有身份/权限/协议层错误才用非 200。

## 5. 登录（后端已实现，前端已对接）

```
POST /api/v1/auth/login
Content-Type: application/json

{ "username": "admin", "password": "123456" }
```

成功：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9...",
    "tokenType": "Bearer",
    "userInfo": {
      "id": 1,
      "username": "admin",
      "realName": "系统管理员",
      "role": "ADMIN"
    }
  },
  "traceId": "...",
  "timestamp": 1789556454657
}
```

前端把 `token` 存到 `localStorage['wms:token']`，把 `userInfo` 存到 `localStorage['wms:user']`，
并在后续请求自动加 `Authorization: Bearer {token}`。

失败：`code = 20004`（用户名或密码错误）、`20005`（账号禁用）、`10002`（参数校验失败，
字段级错误放在 `data` 里，形如 `{ "username": "用户名长度需在 3 到 50 之间" }`）。

### 需要后端补一个接口

```
GET /api/v1/auth/me
```

返回当前登录用户（结构同 `userInfo`）。用途：刷新页面后用 token 重新拉一次用户信息，
以及以后做按钮级权限。前端调用点已经写好（`src/api/auth.js` 的 `getCurrentUserApi`）。

## 6. 基础数据（前端已完成页面，等后端接口）

四个模块 URL 一致：

```
GET    /api/v1/basedata/{resource}         分页查询
POST   /api/v1/basedata/{resource}         新增
GET    /api/v1/basedata/{resource}/{id}    详情
PUT    /api/v1/basedata/{resource}/{id}    修改
DELETE /api/v1/basedata/{resource}/{id}    删除（逻辑删除）
```

`{resource}` 取值：`warehouses` / `zones` / `locations` / `products`

### 6.1 通用查询参数

| 参数 | 类型 | 说明 |
|---|---|---|
| `page` | int | 页码，从 1 开始 |
| `size` | int | 每页条数，可选 10/20/50/100 |
| `keyword` | string | 模糊匹配，各模块匹配字段见下 |
| `status` | string | `ENABLED` / `DISABLED` |
| `warehouseId` | long | 仅 zones / locations 支持 |
| `zoneId` | long | 仅 locations 支持 |

`keyword` 的匹配字段：

- warehouses → `code` / `name` / `address`
- zones → `code` / `name`
- locations → `code` / `name`
- products → `skuCode` / `name` / `barcode`

### 6.2 各模块字段

**warehouses（仓库）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | long | 主键 |
| code | string | 仓库编码，全局唯一，≤32 |
| name | string | 仓库名称，≤64 |
| address | string | 地址，≤255 |
| status | string | ENABLED / DISABLED |
| remark | string | 备注，≤255 |
| createTime | string | `yyyy-MM-dd HH:mm:ss` |

**zones（库区）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | long | |
| warehouseId | long | 所属仓库 |
| warehouseName | string | **建议 VO 里冗余返回**，否则前端靠下拉缓存反查 |
| code | string | 同一仓库下唯一 |
| name | string | |
| zoneType | string | STORAGE / PICKING / RECEIVING / SHIPPING / SORTING |
| sortNo | int | 排序 |
| status | string | ENABLED / DISABLED |

**locations（库位）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | long | |
| warehouseId | long | |
| warehouseName | string | 建议冗余返回 |
| zoneId | long | |
| zoneName | string | 建议冗余返回 |
| code | string | 同一仓库下唯一 |
| name | string | |
| locationType | string | RACK / FLOOR / TEMP |
| capacity | int | 容量上限，0 表示不限 |
| usedCapacity | int | 已用容量 |
| status | string | ENABLED / DISABLED |

**products（商品）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | long | |
| skuCode | string | SKU 编码，全局唯一 |
| name | string | |
| spec | string | 规格，如 500ml/瓶 |
| unit | string | 计量单位 |
| barcode | string | 条形码 |
| weightG | int | 重量（克） |
| shelfLifeDays | int | 保质期（天） |
| status | string | ENABLED / DISABLED |

### 6.3 新增 / 修改的请求体

请求体字段 = 上表去掉 `id`、`createTime`、`updateTime`、`warehouseName`、`zoneName`、`usedCapacity`（库位的 usedCapacity 由库存变动维护，不由前端写）。

示例：

```json
// POST /api/v1/basedata/warehouses
{ "code": "WH001", "name": "上海一号仓", "address": "上海市浦东新区示例路 100 号", "status": "ENABLED", "remark": "示例数据" }

// POST /api/v1/basedata/zones
{ "warehouseId": 1, "code": "A", "name": "A区存储区", "zoneType": "STORAGE", "sortNo": 1, "status": "ENABLED" }
```

### 6.4 删除失败要有明确错误码

如果仓库下还有库区、库位下还有库存，删除应该拒绝并返回业务错误码（文档里预留了 `30012 存在关联数据，无法删除`），
前端会直接把 `message` 弹给用户。**不要静默成功**。

## 7. 命名约定

- JSON 字段一律 **小驼峰**（后端实体开了 `map-underscore-to-camel-case`，VO 直接返回即可）
- 枚举值用**全大写下划线**字符串，和 SQL 注释保持一致，前端 `src/constants/options.js` 已经对齐
- 时间统一 `yyyy-MM-dd HH:mm:ss` 字符串
